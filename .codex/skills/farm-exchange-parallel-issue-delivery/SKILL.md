# Farm Exchange 议题分组与并行交付

调用本 skill 的会话是总控会话：拆分本次选定的 issue，为每组启动独立 Codex 会话（chat/thread），全部交付后汇总整合到 `dev`。分支会话使用 [farm-exchange-engineering-lead](../farm-exchange-engineering-lead/SKILL.md) 的受派模式；其内部可使用开发子 Agent，但子 Agent、CLI session 或后台进程不充当分支会话。本 skill 包含最终独立审查；人工验收和合并授权仍是单独门槛。

## 工作流入口

- 从当前请求取得仓库和 issue 清单；默认仓库为 `Fotally/Farm-Exchange`。缺少清单且无法从对话确定时询问，不复用历史编号或自动纳入全部子任务。
- 只要求划分时交付分组与依赖，不启动开发；要求实施时执行下述闭环。创建本 skill 或说明其用法本身不授权执行任何示例里的 GitHub 操作。
- 读取根 `AGENTS.md`、`.codex/rule-loading.md`、适用目录规则、issue 正文与讨论、关联 PR 和相关接口文档。核对真实远端、当前分支、未提交改动和任务进度，保留其他工作。
- 本工作流使用 **修复分支 → dev**。复用现有工程规范和审查标准；不执行旧提交 skill 中的 `dev → main` 命令，也不修改已有 `dev → main` PR。后续向 `main` 集成另行安排。

## 1. 按真实修改面分组

先读取实际实现、消费者和测试；设计分工前使用可用的 `codebase-design` skill。为每个 issue 列出实现文件、状态拥有者、接口与调用约束、测试辅助、配置/场景/素材及文档的预计修改面。

以下任一情况视为相互影响：修改同一代码或测试文件（含测试辅助），即使位于不同区块；改变另一项使用的接口、状态、执行顺序或测试协议；共同修改配置格式、场景或生成规则；一项必须依赖另一项尚未合入的实现。文件名不同不等于独立。

- 将存在影响关系的 issue 连成组，包含传递关系：A 影响 B、B 影响 C 时，A/B/C 同组。同组使用一个分支，明确先后顺序，逐项串行开发；完成整组后交付一个关联全部组内 issue 的 PR。
- 不同组只有在修改面和调用约束独立时才并行。已合入 `dev` 的依赖作为基线读取，不再视为待开发冲突。
- `AGENTS.md`、文档索引等公共说明由主 Agent 单一负责、逐组更新，不能交给多个开发者同时编辑；仍记录文档交叉及合入后的检查。公共代码不能用“统筹整合”名义拆开并行。
- 输出分组表：issue、影响证据、组内顺序、分支、文件所有权、验收条件、当前状态。已有总入口时更新其进度，保留原范围与其他待办。发现必须调整已确认方案或已公布分组时先与用户沟通，受影响部分等待确认。

完成条件：每个选定 issue 恰好属于一个组，跨组没有未解决的代码或执行依赖。

## 2. 建立分支并启动独立会话

- 每组从最新、已核实的 `origin/dev` 建立 `codex/issue-<编号>-<主题>` 或多 issue 分支，记录基准 SHA；不同组使用独立 worktree。复用现有分支前核对范围与工作区状态。
- 进入派发前读取[多会话编排](references/chat-orchestration.md)，使用仓库 `tools/Invoke-CodexThread.ps1` 连接真实 Codex App Server，检查创建、等待、读取及原会话回传能力。连接失败时报告阻碍，保留已完成的分组/分支准备；不静默切换实施方案。
- 每组创建一个独立会话并绑定其唯一分支与 worktree；启动提示明确调用工程统筹 skill 受派模式。记录真实会话标识与恢复游标，避免重试创建重复会话。默认同时最多三个分支会话，超出时分批；总控统一分配全批最多三名并发开发子 Agent 的预算，分支统筹不得各自再开满三人。
- 分支会话负责本组代码、专题文档、提交前全新 `code_checker`、获准运行的适用验收与本分支提交；总控负责公共说明、验证资源调度、GitHub 写入与最终汇总。公共文档需求由分支会话交回总控，不并行修改根规则或索引。
- 发现跨组实际影响时暂停相关组的交叉写入，说明证据并取得分组调整确认，再集中到同一分支串行处理。

## 3. 等待全部交付并组织返修

- 总控通过会话工具等待并核对每个会话的完整交付：issue、分支/worktree、基准与 head、代码及文档清单、审查、实际验证和证据、公共文档需求、遗留项及“已停止写入”。会话空闲、单个 turn 结束、进程退出或一句“完成”不足以满足交付条件；失败、待用户输入、待审批或缺少证据时仍未完成。
- 等待期间可安排验证资源、处理阻碍及传递信息；只有所有组都完成本轮交付并停止写入，才进入最终汇总，不把先完成的一组提前合并。当存在待决输入时保持阻碍状态并向用户报告，不自动略过该组。
- 汇总发现业务、测试、证据或审查待修项时，用回传工具继续对应的原会话，附准确版本、问题和验收条件；该组状态退回返修，其他组保持停止写入。等待返修会话重新交付，再复核全部组。保留原会话供返修，不将“本轮结束”解释成删除或归档会话。

## 4. 验收并提交到 dev

按当前根规范和 `docs/project/build-and-validation.md` 执行与改动匹配的验收，遵守适用的编译、测试、覆盖率、图形、导出及启动要求。文档/skill 等维护任务按工件和行为演练验收，不自动扩展到无关游戏测试。

- 总控串行分配会争用产物的构建、覆盖率、Godot 与导出运行权；分支会话仅在获准后运行并回报结束，独立 worktree 不代表这些进程可无约束并发。总控补齐公共说明与相应审查，再独立核对各组完整成果。
- 对原故障核对真实结果及相关日志，不仅看退出码；保存本轮证据、覆盖率明细和对应交付树。未运行项与旧版本证据明确区分。
- 只提交本组成果；创建或更新本组 **head 为修复分支、base 为 dev** 的 PR，关联组内所有 issue，写清行为、文档、验证结果及限制。进入本阶段前读取[GitHub 交付与清理](references/github-delivery.md)。
- 核对当前 head 的必需 CI 全部成功。失败先修复并重跑受影响验证；head 变化后重新核对检查，旧版本绿灯不放行新版本。

## 5. 最终独立审查

使用 [farm-exchange-review-pr](../farm-exchange-review-pr/SKILL.md) 的材料要求、默认模型配置和审查标准，审查完整 PR。当前任务已选择本闭环，独立审查是必经步骤，不再询问是否需要审查；不沿用其可选审查入口来跳过此门槛。

- 每轮使用全新的只读审查员，与开发者及前轮审查上下文隔离；提供真实 base/head、merge base、全部文件、原始 issue、确认规则及对应版本证据，不传递前轮 verdict 或预期结论。
- 检查正确性、规则一致、Module 状态归属、Interface 调用负担、Depth/Locality、真实测试与维护成本。审查员不修改文件或 GitHub，不争用验收进程。
- 待修项回传对应的原分支会话，更新代码和中文文档，完成适用验证、CI与全新复审，直到没有待修问题。确有需要延期的事项先由用户确认；不自行把未解决问题写成通过。
- 审查结论绑定 head、目标分支名、merge base 和实际完整差异。任何被审文件、head 或上述审查范围变化都会使旧结论失效，须全新复审；仅目标分支尖端推进而审查范围未变时，核对集成检查即可。报告实际审查范围，将已有运行证据与审查员独立验证区分。

## 6. 人工验收与 dev 集成

提供每组 PR 链接、当前 head、CI、独立审查和验证结果，状态记为“待人工验收”。CI 和独立审查通过不等于合并许可，不启用自动合并。

用户明确批准哪些 PR，就仅合并这些 PR 到 `dev`。授权对应已展示的 head、目标分支和审查范围；批准后 head、目标分支、merge base 或实际完整差异改变时重新验证、审查，并取得该范围的人工确认。已有有效授权无需逐次再问。用户已手动合并时直接查证事实并进入清理。

各组依次集成，后续组读取前组已更新的 `dev`。Git 文本冲突发生在合并完成前：确认原分支会话已停止写入后，由总控在该修复分支 worktree 中解决与最新 `dev` 的冲突并同步文档；需要改变确认方案时仍先沟通。执行前使用可用的 `resolving-merge-conflicts` skill，不在两个会话中同时操作同一分支。集成改动进入适用验证、当前 CI、全新独立审查和新版本人工确认后，才合并该 PR。

若已合入 `dev` 后才发现集成回归，由总控负责在 `dev` 修复、同步文档并完成审查与适用验收；仅有明确属于某组的业务待修时回传原会话，并先移交唯一写入权。修复关联原 issue 或新建对应回归 issue，不能直接推送 `main` 或绕过发布门槛。重新验收完成前保持受影响的 issue 与清理状态待完成。

## 7. 合并后完成清理与关单

按[GitHub 交付与清理](references/github-delivery.md)逐项核实并完成：合并状态和提交、精确修复分支的远端/本地删除、已完成关联 issue 的关闭、总入口状态同步。`dev` 是长期集成分支，任何清理都不得删除它；`main` 与仓库默认分支同样受保护。

不依赖 PR 的 `Closes` 文案推断 issue 已关闭。多 issue PR 逐项核对；仍有未完成范围的 issue 保持开放，总入口有剩余子任务时保持开放。删除分支不附带删除工作区、构建产物或证据。

最终逐组报告：PR 与最终 SHA、验收/审查/CI、实际合并提交、分支清理、issue 开关状态及尚未完成项。记录仅反映查证事实；清理部分失败时明确剩余项，不能标成全部完成。
