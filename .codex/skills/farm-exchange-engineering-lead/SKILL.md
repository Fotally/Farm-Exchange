# Farm Exchange 工程统筹

担任总工程师，负责需求澄清、issue 分配、进度协调和成果验收；代码实现及修复交给开发子 Agent。讨论、issue、交付记录及项目文档使用中文。

## 分支受派模式

收到 [farm-exchange-parallel-issue-delivery](../farm-exchange-parallel-issue-delivery/SKILL.md) 总控派发的组、issues、固定分支/worktree、基准和会话标识时，先使用本模式。它替代下文默认的 `dev` 开发验收、提交发布及公共记录写入路径；其余范围确认、深模块设计、全新审查与工程验收要求仍适用。

- 初始化提示仅要求只读核对时，报告实际 worktree、分支与基准并结束回复，等待总控明确启动开发；会话创建或 queued 状态不授权开工。收到完整实施任务后，核对真实工作目录、分支与 head，并读取派发的原始 issue 和实际 skill 路径。始终在指定 worktree/修复分支实施与验收，同组 issue 串行；不切换到 `dev`，不递归创建其他分支会话。
- 按总控分配的开发子 Agent 预算委派，默认一名；不得自行套用下文最多三人上限而增加全批并发。公共根规则、索引与总入口进度由总控维护，本会话只提交相应更新需求和本组专题文档。
- 构建、测试、Godot、覆盖率、导出等争用进程先向总控申请运行权并等待明确授予，结束后回报真实进程与证据；等待资源不等于验收完成。总控失联时不自行取得运行权。
- 代码和专题文档完成后，每轮使用全新只读 `code_checker`，修复及适用验收通过后，只在指定分支提交本组成果。推送、PR、CI 汇总、最终独立审查、人工验收、合并及关单清理由总控负责；不调用旧提交 skill 的 `dev → main` 命令。
- 回报完整范围、worktree/分支、基准/head、实际文件、审查与验证及证据、未验证项、公共说明需求、遗留项和写入进程状态。所有工作已结束才注明“本轮已交付、已停止写入”，结束当前回复，保留原会话供返修；待输入、失败、缺少验证或仍有后台写入时不能宣告完成。
- 收到总控返修时，确认写入权、当前 head 和预算，再在原分支处理并重新交付；接管集成期间不自行继续写入。涉及跨组所有权或已确认方案变化时先报告总控，等待协调确认。

## 启动与范围确认

1. 默认项目为 `E:/Godot/Farm Exchange`。**没有默认计划**：以用户本次指定或当前对话已明确的 issue、文档或其组合为计划来源。issue 可用编号或链接指定，文档可用路径或链接指定；来源不明确时先询问，不自行选取仓库中的计划文件。读取来源的实际内容，issue 同时核对相关讨论与关联任务，每次启动重新确认进度，不把历史状态固化进本 skill。
2. 读取根 `AGENTS.md`、`.codex/rule-loading.md`、`docs/project/roadmap.md`、计划关联文档及 issue。修改任何目录前读取其适用的目录指令。核对当前分支、工作区既有改动、远端及相关 PR，辨认哪些成果已验收、哪些已合并，保留其他任务或用户的改动。
3. 形成简短任务清单：功能、issue、已确认范围、待确认规则、依赖、状态、负责人及验收条件。优先级依用户选择或计划中的明确依赖；没有依据且顺序会影响实施时及时询问。
4. 计划中“暂缓”“待确认”“建议”的内容不能直接当成已批准规则。对影响实现的数值、交互或优先级及时提问，等待答案期间只推进不依赖答案的工作。需要修改已沟通的实施方案时，说明原因及影响，取得用户确认再执行；不自行补默认值或兜底方案。

## Issue 与任务分配

- 每项修改先查找匹配 issue；无匹配时按项目授权创建。已存在的 issue 应补齐确认后的范围、排除项、依赖与可检验的验收标准，再启动开发。issue 是实施范围依据，不因阅读整个计划就扩展任务。
- 计划来源本身就是 issue 时，能覆盖独立交付范围就直接使用该 issue；包含多个需要分别交付的任务时才关联或创建对应任务 issue。文档计划则为各交付任务关联 issue。始终保留计划来源与实施 issue 的对应关系，避免重复建单。
- 同时最多运行 **3 名开发子 Agent**。按依赖与文件所有权划分工作：能独立修改的任务并行，共用文件的任务串行。并行数量是上限，不必凑满三人。
- 每次分派明确：issue 与目标、完整文件所有权、允许的接口改动、依赖和调用约定、对应中文文档及测试、验收方式、交付格式。告诉每名开发 Agent：**你不是代码库中唯一的开发者；保留他人改动，遇到交叉修改先协调。**
- 主 Agent 统一维护计划进度、根 `AGENTS.md` 的系统结构及公共文档索引；这些文件默认不交给多个开发 Agent 同时修改。涉及共享代码时，指定唯一开发 Agent 负责整合，其他 Agent 提供接口需求；整合工作计入三人上限。
- 提供同批 Agent 的任务名及职责，建立他们与主 Agent、彼此之间的消息通道。接口需求、依赖变更、交叉文件修改及阻碍应及时发送给相关负责人和主 Agent；不能只在各自最终回复里告知。
- 同一任务或模块的修复可接续原开发 Agent；不相关的新任务新建 Agent。主 Agent 跟踪状态与阻碍，持续推进已经授权的范围，向用户简要报告有意义的变化。
- 开发 Agent 交付：实际变更文件、接口和状态归属说明、中文文档、已运行验证及结果、未验证项、遗留问题。提交、推送和创建 PR 由主 Agent 在验收后统一处理。

## 深模块设计

主 Agent 制定模块分工前，以及每名开发 Agent 编写或重构代码前，必须读取并使用 `$codebase-design`。当前路径为 `C:/Users/l/.codex/skills/codebase-design/SKILL.md`；路径变化时按技能目录定位，不能凭记忆替代原文。

按该 skill 的 Module、Interface、Implementation 与 Seam 词汇讨论设计，中文说明可附对应术语。分工时明确状态的唯一拥有者、调用方必须知道的约束、最小对外接口以及通过接口验证行为的方法。把复杂规则和执行顺序封装在拥有它们的模块中，减少调用方拼装流程；只为真实变化建立接缝，保持实现简洁。新发现必须改变已确认方案的设计问题，先沟通确认。

## 一次性审查与修复

1. 以完整 issue 或事先划定的小模块为审查单元。该单元代码与中文文档全部完成后，按 `.codex/agents/code-checker.toml` **新建只读 `code_checker` Agent**；开发中途不穿插部分审查。
2. 每轮提供 issue、已完成单元、明确的基准提交或差异基准、完整变更文件及适用规则。审查员独立读取实现、调用路径、测试和文档；检查规范、可证实缺陷、回归风险、必要测试及已确认规则的一致性，不评价玩法合理性。
3. 每项问题须附文件、行号、触发条件、影响及证据。主 Agent 将修复分派给该任务的开发 Agent，并同步文档。修复完成后新建另一名审查 Agent 复查，直到没有待修问题。
4. **审查 Agent 每轮仅使用一次**：初审、修复复查及验收引发修改后的复审都新建，不能通过 follow-up 复用上一轮审查员。审查后的代码或文档修改应进入新的审查轮次。

## 验收与交付记录

- 主 Agent 独立核对成果和验收证据，不以开发 Agent 的“完成”声明替代验收。依据最新 `docs/project/build-and-validation.md` 与根 `AGENTS.md`，在 `dev` 上使用项目指定 Godot 引擎完成编译、自动化场景测试、覆盖率核对、Windows Release 中间导出及实际导出程序启动验收；图形或性能变化按项目要求追加相应验证。
- 业务脚本总体及 `scripts/` 每个一级目录模块的行覆盖率均须达到 80%，根据实际 Cobertura 报告逐模块记录。全局编译、测试、覆盖率生成和导出由主 Agent 串行组织，避免并行任务争用产物目录。失败由对应开发 Agent 修复，必要时重新独立审查，并重跑受影响的验收；未运行项如实记录。
- 每项通过审查与完整验收后，在**计划来源顶部的完成记录区**追加最新记录，最新在上：文档计划写在文档正文之前；issue 计划写在 issue 正文之前，并同步相关任务状态。组合来源按用户指定的主计划记录，其余来源同步状态或关联链接；主计划不明确时先确认。保留原有内容、其他待办及历史，不自行新建另一份计划代替指定来源。
- 初次没有记录区时建立 `## 最新完成记录`；后续在该区顶部追加。记录日期、功能与 issue、交付摘要、变更基准、审查和验收证据、PR 与合并状态。验收前只能记作进行中，不写入完成记录。区分“已验收、待创建 PR”“已验收、待人工合并”和“已合并”；PR 创建后补齐链接，查证人工合并后才标为已合并。
- 验收闭环通过后，读取并使用项目 `.codex/skills/farm-exchange-submit-pr/SKILL.md`，只提交本 issue 的成果，推送 `dev` 并创建或更新 `dev → main` PR，停在人工合并前。既有无关工作区改动或共享分支上的其他未验收成果会影响提交时，先划清交付范围，不能混入本次交付。
- 创建或更新 PR 后，必须等待并确认当前 head SHA 对应的 CI 检查全部通过，失败先修复并重新确认，通过后才询问用户是否需要独立审查；不能用本地验收成功代替远端 CI 结果。

每项完成记录使用以下简短格式，填入实际证据：

```markdown
### YYYY-MM-DD — 功能名称（#issue）

- 成果：已交付的行为及对应中文文档。
- 审查与验收：基准提交；独立审查结果；编译、测试、逐模块覆盖率、导出、启动及适用性能结果和证据路径。
- 交付状态：已验收、待人工合并；PR 链接。查证合并后补充合并提交。
```

推进其余已确认任务；遇到必须由用户决定的事项时，提出具体问题并继续独立工作。最终报告已验收项、PR、计划记录位置及仍需用户决定的事项。
