# 独立审查 Farm Exchange PR

目标是审查已提交的真实版本，说明实现是否符合已确认规则、Module 是否有 Depth，以及这次变更给未来维护带来的具体收益和成本。结果用中文。

## 先确认是否审查

1. 在创建或更新 PR 后进入本 skill 时，先告知真实 PR 链接、当前 head SHA 与已完成的验收结果，然后询问用户是否需要独立审查。
2. 问题明确目标 PR 与版本、下节默认模型配置，以及审查范围为代码正确性、深模块设计和维护成本。可用交互提问工具时，提供“进行独立审查”和“暂不审查”；工具不可用时在最终回复中提出同一问题并等待回答。
3. 只有用户同意后才委派。拒绝、未回答、提问超时均保持 PR 已交付、等待人工合并的状态；不启动审查，也不把审查写成通过。
4. 用户已经明确要求审查或重新审查同一个 PR 时，直接执行，不重复询问。仅调用 skill 名、接受其默认提示或要求“提交 PR”均不等于同意审查。
5. 授权以具体 PR 为单位，不把一次同意扩大为以后所有 PR。用户已同意该 PR 的审查，随后又要求修复时，该修复的独立复审沿用授权，每轮仍新建审查员。

自动发现本 skill 只是进入上述判断；“先询问”与“只能显式调用”是不同约束，保留正常技能发现能力。

## 准备真实版本与原始材料

主 Agent 在委派前完成以下收集；只读查询 GitHub 不需逐次征求许可。

- 核对目标 PR 的仓库、链接、状态、base/head 分支及完整 SHA；记录用于比较的 merge base SHA。
- 从 PR 实际提交取得完整变更文件和差异，默认审查完整 PR。用户明确限定本轮增量时记录范围，同时提供理解调用关系所需的完整实现。
- 取得关联 issue、用户已经确认的方案、适用的根及目录 AGENTS.md、相关中文接口和实现文档。
- 标明现有测试、覆盖率、性能或导出证据对应的 SHA／交付树；不把旧版本报告自动当作当前版本的证据。
- 记录当前工作区与 PR head 是否一致，以及不属于 PR 的未提交改动。用 `git show <SHA>:<路径>`、`git diff <merge-base-SHA> <head-SHA>` 等指定版本读取，保持现有分支和工作区不变。

材料齐备的标准：另一名 Agent 能独立定位被审版本、全部变更和判断依据，不必依赖主 Agent 的结论。缺少必要材料时先补齐；无法取得时准确说明缺口。

## 委派独立子 Agent

默认调用配置仅在此处维护：

```text
collaboration.spawn_agent(
  agent_type="default",
  model="gpt-6.1-sol",
  reasoning_effort="high",
  fork_turns="none",
  task_name=<本轮唯一名称>,
  message=<按下列要求填写完整任务>
)
```

用户明确指定其他模型或推理档位时尊重其选择。指定能力不可用时，报告并等待用户选择；不静默改模型或改为主 Agent 自审。

项目 `code_checker` 角色固定使用另一模型。本 skill 的提交后独立审查与提交前检查并列，采用默认 Agent 角色和上述配置，不修改 `.codex/agents/code-checker.toml`。

每轮使用全新 Agent，隔离前轮推理；不复用上一轮审查员。主 Agent 不传递前轮结论、疑点清单或预期答案，只提供原始材料、用户关注点和已确认规则，让其独立判断。

任务消息必须写入实际值，不只发送占位模板：

- 工作区绝对路径、仓库及 PR 链接、关联 issue、base/head 与 merge base 的完整 SHA。
- 本轮完整范围、所有变更文件、指定提交读取方式、无关工作区改动说明。
- 适用规范、用户已确认规则与关注点、中文文档位置、已有验收证据及其版本。
- 要求先读取本环境可用的 `codebase-design/SKILL.md`，用其 Module、Interface、Implementation、Depth、Seam、Locality 概念审查。
- 下节审查标准、只读约束和返回格式；返回结果必须注明实际审查 head SHA。

审查员仅阅读实际代码、调用方、测试和文档。保持只读，不修改文件，不启动全局构建或 Godot，不提交、推送、评论、审批或合并 PR。

## 审查标准

审查完整变更及必要调用上下文，而非只检查新增类或单独计算函数数量：

- **正确性与一致性**：可从真实路径证明的状态、边界和回归问题；已确认规则、正式执行路径、测试及中文文档是否一致。
- **Depth 与 Locality**：Interface 是否隐藏实质复杂度；状态是否有唯一拥有者；修改规则时知识、代码和验证能否集中，而非散落调用方。
- **调用负担**：除方法参数外，检查调用顺序、默认参数、隐式依赖、错误模式和性能要求；是否让调用方重复公式或拼装本应由 Module 完成的事务。
- **配置与 Seam**：配置解析、验证、创建和实际执行是否连贯；测试是否能通过真实 Interface 改变行为，局间状态是否隔离；只为真实变化建立接缝。
- **快照与缓存**：不可变性、引用稳定性、失效条件及性能契约是否由拥有者明确维护；读取方是否依赖未经记录的约定。
- **验证与维护**：测试是否检查真实结果和边界，夹具是否依赖无关的文本排版；配置字段扩展、规模调整等实际维护场景是否有明确文档与必要证据。

按适用项目规则核对覆盖率、性能和构建证据，不把某次功能的数值或门槛推广成技能固定规则。已有验收报告不等于审查员重新运行过验收。

从全局调用关系判断设计，结合真实变更场景说明权衡。不要以代码行数衡量 Depth、评价玩法合理性、提出假想框架或将“最小补丁”当作唯一设计目标。

## 返回与核对结论

审查员返回：

1. 实际审查的完整 head SHA、范围及读取材料。
2. 按严重程度排序的待修问题，区分阻断问题和非阻断维护建议；每项附准确文件与该提交行号、触发条件、实际影响、证据和合理的改进方向。
3. 用户关注的改进是否落实，Depth／Locality 的具体收益、局限和新增维护成本。维护成本对应真实可预见的变更场景，避免泛泛罗列。
4. 未能验证的事项；没有待修问题时明确写“未发现待修问题”，仍给出判断依据，不把无阻断问题等同于设计完美。

主 Agent 核对证据、版本和范围后报告。返回 SHA 不符时，不将其结论作为当前 PR 通过；重新确认并新建独立审查员。期间 head 变化一次可重新取得材料复审，连续变化时先说明已审版本与结论范围，等待版本稳定。

审查本身不授权自动修复代码或更新 issue／PR。用户要求修复后，按 issue 与方案确认、实现和中文文档、全新独立复审、适用验收、`farm-exchange-submit-pr` 流程处理；跨出已确认方案的设计变更先沟通。

最终中文回复给出 PR 链接与审查 SHA、逐项落实结果、深模块判断、具体维护成本、待修问题及未独立验证项。保留人工合并状态。
