# 自然天气循环排程实现

本文履行[天气模块 Interface](interface-weather-system.md)，设计数值只在[地区天气](../../gameplay/world/weather.md)与正式 JSON 维护，不将本页作为第二份参数表。

## 一次预排

`WeatherRules.Parse` 在模块内部完成 JSON 描述解析、全部数值与容量校验，再构造只读配置值。正式共享 `Default` 也使用这个入口；它只代表已验证配置值，不代表共享运行局。经营组装点为每局选定同一份配置，`WeatherSystem` 构造明确接收该值，不自行访问默认配置。配置可以共享，执行器内部的排程数组、活动列表、事件位置与查询字典始终每局独立。

构造自然局时创建独立 `System.Random(seed)`。从零日之后开始，每次抽取候选间隔、持续、宽高、地图内位置与类型。多云／降雨选择读取 JSON 的 `CloudyWeight`／`RainWeight`。无论候选是否被接纳，下一候选仍在当前候选开始日之后推进，不因冲突重抽位置或持续时间。

候选开始／结束日期以 `GameTimeUnits.PerDay` 和 `PerSecond` 转换到首个到达日期的经营秒。周期要求与正式日历一致且秒数为整数；当前周期完整环绕精确时间，重复时不累计取整误差。活动区间为 `[start, end)`，结束和另一事件开始恰在同秒时不构成时间重叠。

## 完整存续区间与接缝

接纳一个候选时，将既有事件分别平移 −1、0、+1 个周期，与候选原区间比较。持续必须短于周期，因此这三个位置完整覆盖循环空间冲突；候选跨周期尾部时也会检查与已接受周期开头事件的冲突。

若存在时间重叠且矩形相交，直接拒绝。无空间冲突时收集重叠事件的时间区间，检查候选开始以及区间内所有既有事件开始时刻的并发数量；数量只可能在这些开始时刻上升，因此这些时刻足以检查完整存续区间。候选不被裁短，未接纳的候选不进入正式表。

当前固定地图与候选规模使用简单数组和局部区间集合即可。未建立通用叠加矩阵、灾害框架或可编辑未来排程。

## 预排规模变更的建局验收

`BuildSchedule` 逐候选生成，并在接纳检查中遍历已有排程的完整存续区间。周期变长或候选间隔变小会增加尝试次数，持续、尺寸和活动上限也会影响已接纳排程数量与检查成本。配置数学上合法只表示规则与数值可以执行，不能据此认定任意规模都适合启动。实际调整这些参数时，保持生成算法与公开 Interface，在同一环境、同一种子下比较修改前后配置的真实自然模式构造成本。

文件读取、`WeatherRules.Parse` 和 JIT 预热均放在采样之前；如果需要评估加载成本，应单独记录，不与预排构造混算。可以在既有 Godot 测试上下文中，对已经解析的配置执行以下采样，不需要读取私有排程或新增诊断框架：

```csharp
// rules、seed、sampleCount 由本次对照配置与采样安排明确给定。
_ = new WeatherSystem(seed, rules, WeatherMode.Natural); // 采样外预热
for (int sample = 0; sample < sampleCount; sample++)
{
    long allocatedBefore = GC.GetAllocatedBytesForCurrentThread();
    long start = System.Diagnostics.Stopwatch.GetTimestamp();
    var weather = new WeatherSystem(seed, rules, WeatherMode.Natural);
    double elapsedMs = System.Diagnostics.Stopwatch.GetElapsedTime(start).TotalMilliseconds;
    long allocatedBytes = GC.GetAllocatedBytesForCurrentThread() - allocatedBefore;
    GD.Print($"样本 {sample}：周期 {weather.CycleSeconds} 秒，构造 {elapsedMs:F3} ms，线程分配 {allocatedBytes} bytes");
}
```

两份配置使用相同种子列表、样本数量、构建模式与采样条件，分别预热后采样；记录每个样本，不能只保留最好的一次。线程分配指标只统计当前线程的托管分配，不能当作整个进程的内存峰值。证据保存到既有 `build/` 或 `coverage/` 目录，包含实际输入配置、种子、Godot／.NET 版本、构建模式、操作系统与硬件、采样安排和修改前后结果；配置与种子用于复现，不向玩家公开未来排程。根据实际变化评估启动成本，不引入未经确认的固定阈值或任意规模上限。

下文 `--weather-query-probe` 测量的是已经建局后的整田查询，不能替代这里的预排构造耗时。字段扩展时的描述、只读属性、复制构造与校验维护约定见[配置 Interface](interface-weather-system.md#配置字段扩展与规模变更)。

## 执行与快照

构造后不保留生成用随机对象。首次周期只使用本周期已经开始且未结束的事件，保持零秒晴天；第二周期开始后按模周期相位额外启用前周期合法尾部。结束不清除其他区域，也不存在被覆盖天气恢复。

预排同时生成首周期与循环的有序去重事件边界。`GetNextEventSeconds` 二分查找严格晚于当前相位的生效／结束点，并在末尾环绕；首周期边界排除前周期不存在的尾部结束。`AdvanceTo` 在下一事件之前直接保留快照，只有跨过事件才扫描预排并同步当前活动区域，因此每经营秒不扫描整张表。

快照列表只读，区域是不可变值；活动组合没有变化时复用缓存。地图按真实活动列表表现，经营按真实基础格／整田查询供水与积分，没有第二份全图雨布尔状态。

这里的稳定引用是[生产者 Interface](interface-weather-system.md)的性能约定：状态未变化继续发布同一对象，真实变化发布新对象，旧对象永远保留旧内容。消费者可以以 `ReferenceEquals` 判断是否需要刷新派生表现；不能在原列表上增删后保留引用，也不能每次查询复制列表导致所有消费者重复重建。一次跨越多个事件但最终活动组合相同，可以保留原快照；不为已经结束的中间表现追补通知。

基础格和整田查询使用只读列表的索引访问，保留土地模块提供的完整占地偏移与雨优先规则。满地图多个经营相位会重复调用查询；索引访问避免通过接口枚举器遍历时产生逐格分配，查询本身不新建列表、枚举器或派生几何。

`GetFarmWeather` 将九格聚合结果存入模块内部的锚点字典。键是土地模块的 `AnchorIndex`，值仅为天气枚举；当前所有农田在同一锚点拥有相同固定占地，朝向不改变此几何，因此重建无须保留原实例对象。调用先验证农田类型，再查字典；未命中才使用真实 `Footprint.Offsets` 逐格查询，命中不重复扫描九格。字典只记录实际查询过的地图锚点，不持有农田或占地第二份状态。

自然执行比较新旧活动快照，仅在组合实际改变时替换快照并清除派生字典。显式设置、清除成功必清除字典；拒绝路径在任何修改之前返回。没有增加外部缓存成员、建拆通知或几何副本。

## 事件边界与查询职责

当前经营推进已经使用天气开始／结束作为真实事件边界：`FarmGame.AdvanceTicks` 只在边界之前批量累计同一天气，边界秒仍执行原完整经营相位。天气执行器在事件之前直接返回已有活动状态，不每日轮询整张预排。每田查询只在该轮活动组合下第一次计算九格聚合，之后命中模块内部字典。

保留权威查询，而不向每座农田推送天气通知，原因是天气变化与供水需求并不等同。持续雨期间收获会清水，下一秒仍要再次按当前降雨供水；新建或同锚点重建的农田也必须立刻查询当前天气。仅通知天气开始／结束不能覆盖这些情况；订阅方案还要维护建拆注册、播种／收获后刷新和另一份建筑天气状态。现有查询让天气唯一拥有天气，农田唯一拥有水分与生长，两类状态无需相互同步。

因此 `FarmingSystem.AdvanceGrowth` 与 `AdvanceQuietSeconds` 必须显式接收本秒／平静区间查询结果，晴天也由天气模块确认；农田推进函数不隐式假定晴天。天气事件不会直接调用农田或加工操作，供水、正常收获及换季促熟仍由原经营相位协调。加工建筑当前没有天气业务效果，不为假想受影响建筑增加订阅框架。

## 显式局

显式局构造空排程，所有查询仍使用同一当前活动矩形列表。设置和清除先完整校验，再替换只读快照；自然模式、无效类型、越界、空间冲突、上限或不匹配移除均返回中文拒绝且保持旧快照。显式矩形支持全图测试，持续到明确清除。

## 查询成本诊断

专用场景 `tests/unit/test_weather_system.tscn` 接受显式参数 `--weather-query-probe`，通过公开 `GetFarmWeather` 查询满地图 8192 座农田，分别测试无活动区域和图形验收使用的雨／云／离屏雨三区。测量区分首次冷扫和随后 16 经营秒×每秒三相位的 48 次热扫：冷扫逐田与九格公开位置查询结果比对，记录其耗时与分配；热扫记录总耗时、P95 单次全场查询耗时、当前线程分配字节及一致的校验和。查询方法的 JIT 预热与强制 GC 在采样之外进行。

输出写入 `coverage/weather-query-probe/performance.json`，改动前后的数据由验收流程保存到既有产物目录。此探针仅在专用场景显式调用时执行；日常 `RunChecks` 继续验证业务行为，实际图形帧间隔门槛由1080P天气性能场景验收。
