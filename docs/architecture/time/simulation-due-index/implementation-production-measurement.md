# 真实生产到期负载验证

关联 [#65](https://github.com/Fotally/Farm-Exchange/issues/65)，履行[到期索引接口](interface-simulation-due-index.md)。入口为 `tests/performance/TestProductionDueLoad.cs` 及 `test_production_due_load.tscn`，也由统一 `TestSuite` 调用。

## 负载与正确性

每组通过真实模块接口建立 8,192 块农田及 8,192 处加工场地，共享容量为 16,384 的正式 `SimulationDueIndex`。农田正常放置、供水及播种，加工场地从真实库存领取九份原料开批，不直接注入完成目标或使用基准状态设置入口。

两组均使用小麦，从 `CropCatalog` 的具名字段读取生长日数及加工半日数。当前生长为 16 日、5,760 时间单位，向上取整为 823 经营秒；加工为四个半日、720 时间单位，向上取整为 103 经营秒。夹具分两个循环初始化，通过实际错峰开工对齐完成秒，不修改生产时长。

集中组全部农田在第 0 秒开工，全部加工在第 `823−103＝720` 秒正常领取开批，双方均在第 823 秒完成。稀疏组八块农田在第 0 秒、其余农田在第 1 秒开工；八处加工在第 720 秒、其余加工在第 721 秒开工。因此第 823 秒只有 16 项到期，剩余 16,368 项在第 824 秒到期。代码从真实目录值计算错峰时间，并分别检查早、晚两组的加工精确目标向上取整后与对应农田目标一致；初始化同步三个模块的时钟，且不得越过任何已登记预约。

测量分别覆盖到期前一秒的平静推进、首批到期和稀疏组尾批到期。每段通过索引读取真实到期锚点，调用所属模块完成，再将实际结果入库；生产模块自行取消成功预约。每个实例只允许完成一次，结束后在计时区间之外全量检查完成集合、农田阶段、加工锁定批量、只读剩余秒数、挂起事件数量和库存。所有实际产量必须完整入库，加工必须等量产出九份；首批及尾批必须在准确目标秒全部完成。

## 测量口径

每组预热一次，再测量三次。`Stopwatch.GetTimestamp()` 记录模块时钟推进、索引推进、逐项读取、真实完成、入库和轻量正确性检查的整段耗时；`GC.GetAllocatedBytesForCurrentThread()` 的区间差值记录该热区当前线程分配。构造、播种、开批、全量结束状态核对、结果对象创建、序列化和打印均在测量区间之外。

成功到期读取数、农田完成数和加工完成数是测试实际调用及返回结果计数。读取调用数还包括每段最后一次返回 false 的查询。它们不是全游戏访问量，也不是模块内部数组读写次数。正式 `AdvanceTo` 不扫描生产实例、`CompleteGrowth`/`Complete` 只访问指定实例的结论由对应源码核对，测试没有添加通用业务观测接口。平静段读零个到期项不代表其他游戏阶段没有扫描。

每次执行覆盖写入 `build/issue65-validation/production-load.json`，保存所有样本的目标秒、真实完成数、剩余预约、库存、耗时和分配，不只保留平均值。没有人为设置耗时或分配通过阈值；是否通过取决于真实生产正确性，耗时与分配用于诊断和前后比较。不同机器、Debug/Release、覆盖率及后台负载的数据不能直接当作相同运行条件比较。

## 与其他验收的关系

本场景使用恒定晴天，不执行天气变化、降雨、工人、全场空闲领取、计划、报价、日志和 UI，隔离生产计时及到期结算成本。它不验证完整 `FarmGame` 阶段编排，不测图形 FPS，也不代表全游戏零分配。满地图 50 tick 与 1080P 图形验收仍由既有负载及 FPS 场景独立执行。

编译后可单独运行 Godot 的 `res://tests/performance/test_production_due_load.tscn`，或执行包含此入口的标准 headless `TestSuite`。JSON 是本地验收工件，不随测试源码重复提交。
