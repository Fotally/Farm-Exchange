## 两日如何计时

主指标从空田具备当前播种条件、开始等工的时刻，计到本轮已播种且供水完成、进入生长的时刻。新建、收获后或改种后的空田均按这一口径；有留水时，播种完成即为结束点。另记录播种完成至供水完成的时长，防止只检查后一段而遗漏长时间闲置。

按经过的模拟时间统计，不按跨了几个日历日期统计；暂停不累计。一天为 `360/7` 秒，两天为 `720/7` 秒。两个整秒事件相隔 51 秒以内达到一日目标，102 秒以内满足两日上限；103 秒已经超过两日。发生在两次步进之间的建造等命令，从该命令时的累计模拟秒开始记录，下一步才获得一次移动或工作进度。

不适季或计划休耕禁播属于等待条件，不计成等待工人；条件转为允许时开始这一轮计时。剩余适宜时间不足只提示预计成熟风险，当前适季且启用播种的空田仍从真实等工时刻计时。排队后进入禁生季节、休耕禁播、玩家立即改种、拆除或越季失败时，该轮终止并单列原因，不能把它当成按时成功，也不能靠反复重置计时宣称达标。正式节奏验收采用季节时间充足、布局稳定的连续生产场景；另外独立验证边界失效行为。

## 稳定轮转与时间预算

沿用现有按锚点索引的循环游标，空闲时从游标起找第一块有有效工作需求的农田，不采用最近优先。认定目标后把游标移动到该格之后；一趟最多完成这块田的播种和紧接着的浇水，再找下一块田。已有干燥待水作物只做浇水。正在生长或播种条件不允许的农田跳过；取消无效任务后继续游标，不从地图开头重来。

每步首先验证当前任务。若失效，当步就可选择新的有效任务。选取任务不单独增加等待秒；这一秒可以计入移动，零距离则可以计入工作。移动和播种、播种和浇水分别占不同完整秒，不在到达的同一秒额外完成工作，也不把同一秒算成两个动作。无工作时留在当前位置。

这一规则让每块有效农田至多等待一个完整轮转，不因距离远而不断被近田抢先。以下是需要后续测试验证的保守预算，不是已测结果：

| 验收布局 | 每趟最大移动 | 每田最大播种供水 | 8 田同时等工、初始空闲 | 包含一项已有工作剩余的保守上界 |
| --- | ---: | ---: | ---: | ---: |
| 工人与 8 田均在同一 4×4 标准田跨度矩形内 | 3 秒 | `3+1+1=5` 秒 | `8×5=40` 秒，约 0.778 日 | `5+8×5=45` 秒，0.875 日 |
| 工人与 8 田均在同一 8×8 标准田跨度矩形内 | 7 秒 | `7+1+1=9` 秒 | `8×9=72` 秒，1.4 日 | `9+8×9=81` 秒，1.575 日 |

上界额外计算一项已有工作的全部耗时，再计算最多 8 田的完整照料，因此包含新需求在工作过程中出现的等待；没有把排队时间省略。`81×7=567 < 720`，满足两日预算；`45×7=315 < 360`，达到一日目标。雨水和已有水分只会减少动作。默认三块相邻中心农田属于更小的布局。

预算从真实等工起点计到供水完成，最多计入一项已在进行的工作；8 块田均适季且剩余适宜时间充足，任务期间没有改种、拆除、重建等重置。工人没有先去矩形外处理其他田，且统计期间不新增矩形外任务。这份保证不等于单工人对全地图 16,384 田的保证；变更任务或超出布局规模的场景不在本预算保证内。满地图性能夹具继续验证负载与生产推进，不能替代上述节奏验收。

## 已确认的最小多人策略

三个工人按固定编号依次处理本秒进度；每名工人都获得完整的 1 秒，先后顺序只是确定性执行顺序，不把这一秒分成三份。共用一个按锚点索引循环的游标，空闲工人只选有效且尚未被认领的农田。选中即认领并推进游标，后处理的工人立即看到该认领，不会再次选同一田。

认领以整块田的本轮工作为单位：移动、播种、原地紧接浇水由同一工人连续完成。雨后湿田播种完就释放；原本待水的田供水完就释放；动作完成或任务失效都释放。只保留这一份认领关系，不增加工作队列、每人固定田区或第二套分配表。农田提供真实需求和有效目标凭据，认领表由 `WorkerScheduler` 唯一维护。

三个起始位置固定为 (190,190)、(193,190)、(196,190)，并按编号 1、2、3 推进。工人之间不碰撞、不相互阻塞，也不预留移动路径；可以交叉或短暂重叠显示。与建筑一样，实际工作只由经营任务与农田状态决定。

每秒先统一检查三个已有任务，释放失效认领，再按固定编号推进各人；这样低编号工人不会因高编号工人的失效认领尚未释放而多等一秒。一个工人本秒完成动作后，下一秒才给新任务计时，仍不重复使用同一秒。工人分配可能不均匀，公平性指田块按同一游标获得机会，不要求三人每轮恰好各做 8 田。

### 三工人的预算

总共 8 田是交付保守基线，不高于已确认单工人规模。三工人共用游标、跳过认领且不会闲置等待有效目标时，增加工人不会强制插入重复任务；8×8 布局内沿用单工人的 81 秒上界已经足够。

总共 24 田的两日验收目标，其证明不能按每人固定 8 田来算：令每次完整照料上界 `B=9` 秒，三人起点和全部目标都在同一 8×8 标准田跨度矩形内。稳定轮转下，一块持续有效的目标之前最多排入其余 23 田；为包含计时起点正在做的工作，额外保守算入至多 3 项既有工作。因此，包含目标在内最多计入 `24+3=27` 项，每项不超过 9 秒。

只要目标尚未被分配，三个工人都有可做工作，不会空闲。将这些项目按实际释放时刻依次交给最先空闲的工人：在目标排到的第 `k` 项被分配前，至少一人此前获得的项目数不超过 `floor((k−1)/3)`；该人的累计占用不超过这个数量乘以 `B`，最先空闲者的可用时刻不会更晚。目标完成时刻不超过 `ceil(k/3)×B`，故即使目标排到第 27 项，也不超过 `ceil(27/3)×9=81` 秒。项目长短不同或人数间任务数不相等，不改变这个上界。

若三人起始空闲、24 田同时等工，不计既有工作，预算为 `ceil(24/3)×9=72` 秒。若计时起点有三项既有工作，预算为 81 秒，即 1.575 游戏日，仍低于两日。该算式不是实际测量结果，必须用确定性经营测试验证异长路线、不同完成时刻和持续复种，不能只测人为平均分工的场景。

预算继续要求所有田适季且时间充足、无任务重置、无矩形外任务。最快的萝卜生长期也超过 200 秒，因此在这一段不超过 81 秒的等待窗口中，已完成照料的田不会收获后再次插入一项工作；若有尚在生长的田后来收获，仍属于这至多 24 块田各自的一项需求。雨水可以缩短任务，不能产生额外播种或重复供水。24 田放不进 4×4 标准田跨度矩形，不能用单工人的 4×4 一日预算宣称 24 田一日达标。

## 状态与小 Interface

`WorkerScheduler` 唯一持有三个工人的格位置、共用轮转游标、各自当前目标、移动与工作剩余时间，以及田块认领关系。`FarmingSystem` 唯一持有作物、水分、生长及目标有效性；`FarmGame` 保持既有降雨、生产、领取、工人、换日换季的相位顺序。

原 `WorkOne` 已替换为下列 Interface；完整成员约定见[WorkerScheduler 接口](interface-worker-scheduler.md)：

| Module / 成员 | 调用方必须知道的约定 |
| --- | --- |
| `WorkerScheduler.AdvanceOneSecond(farming, calendar)` | 在既有工人相位调用一次，内部给三人各推进完整 1 秒，完成需求选择、认领、有效性重验、移动、工作及释放；返回本秒是否至少一人真正完成播种/供水，不把单纯移动计为 `WorkerActed`。 |
| `WorkerScheduler.GetSnapshots()` | 按固定编号只读返回三人的位置、目标格及空闲/移动/播种/浇水状态；不推进经营，不暴露可变工人集合。 |
| `FarmingSystem.GetWorkNeed(index, calendar)` | 只读返回无工作、播种或供水，以及有效目标凭据；空田当前适季且启用播种才有播种需求，预计时间不足不拒绝。已播种待水田在禁播时仍提供供水需求；播种判断共用 `PlantingRules`，不复制季节算法。 |
| `FarmingSystem.TryCompleteWork(request, calendar)` | 按指定动作和目标凭据重验后完成一个动作；失效返回失败且零修改，不把过期浇水自动改成播种。人工供水仍复用现有 `SupplyWater`。 |

这里的 seam 放在农田“查询真实需求、完成指定工作”与工人“安排并耗时”之间，不要求新增 C# `interface` 类型、事件总线或可替换调度 Adapter。`FarmGame` 只组合一个经营步进；UI 不选择任务、不扣移动秒、不直接提交农田动作。

### 保持稳定 Interface，允许内部策略演进

用户已要求未来换成更复杂策略时尽量保持 Interface。`FarmGame` 固定调用 `AdvanceOneSecond(farming, calendar)`，表现层固定读取 `GetSnapshots()` 的经营结果；它们不传轮转游标、认领容器、策略类型或路线排序，也不依赖每人负责固定 8 田。8 田和 24 田是当前参数下的验收规模，不是 Interface 中的田区分配规则。

当前在 `WorkerScheduler` 的 Implementation 内用私有 `SelectNextWork(...)` 集中完成稳定轮转选择；认领、目标校验与移动/动作推进分别保留在其内部。未来选择更复杂的优先级或路线排序，首先替换这个内部选择位置，继续消费农田的真实需求和凭据，而不是让 `FarmGame` 或 UI 拼接算法。农田需求只表达“此目标现在需要何种动作”，不携带轮转优先级或路线成本。

这是一处实际需求明确的内部 seam；当前只有稳定轮转一种 Implementation，因此不新增 `IWorkerStrategy`、策略注册器、依赖注入框架或外部策略配置参数。未来出现第二种真实算法时再判断是否需要具体 Adapter。任何新策略都必须继续履行不重复认领、执行前重验、固定模拟时间及快照只读的 Interface；若改变两日保证或玩家规则，应先沟通并重新验收，不能因保持方法名不变就悄悄改变已确认语义。

道路当前只用于布局，本批为三基础格每秒、不依赖道路连通。用户已说明未来道路可能影响移动速度或属性；因此移动耗时计算与方向留在私有 `BeginWork`，每秒位置推进留在私有 `AdvanceTravel`。未来真正确认道路属性时，由经营组装提供必要的只读土地信息并优先调整这些内部位置，保持 `AdvanceOneSecond` 与 `GetSnapshots` 不泄漏道路类型或速度乘法，UI/NPC 继续只显示结果。当前不猜道路倍率，也不创建恒返回 1 的浅 Module 或可插拔道路策略。

目标凭据用于同格拆除重建、改种、轮次与播种启停的真实变化：农田维护本格局部版本，在新建、拆除、强制改种重启、播种启停改变、收获进入新轮及越季清理时使旧凭据失效，调度器保留领取时的版本。不建立全局实体标识框架。手动立即改种使用 `RestartCrop`，同品种也中断本轮并取消旧任务；兼容内部 `SetCrop` 的同品种调用仍保持无变化，不能将它用于替代手动立即改种。重复设置相同播种启停值不改版本。执行前既检查版本，也检查本轮是否仍需该指定动作；不能只凭目标格相同就执行旧任务。

## 状态变化与表现

移动或工作期间拆除、拆除后同格同品种重建、立即改种（含同品种）、播种启停改变或越季失败，都使旧任务失效；下一工人相位先丢弃旧任务再继续分配。休耕禁播仅阻止空田播种，已播种本轮仍可重新领取有效浇水任务。取消时保留已经到达的实际位置，不回退、不瞬移。目标变更在农田模块使凭据失效，因此后续旧动作不能重新播种或给新对象供水。

降雨仍在本秒开始供水。浇水任务若已被满足，取消剩余移动或工作，不重复供水、不重置生长；播种任务遇到雨水仍可继续，完成后直接生长并省去浇水。实际播种重验当前季节、播种启停与指定任务版本；预计成熟只用于风险提示，不拒绝当前适季的播种，也不预测未来天气。风险估算中干田最低预留 1 秒供水，与本方案的紧接 1 秒浇水一致。

表现层读取只读经营快照，使用现有 `MapCoordinates` 与 `WorldMap.GetCellWorldCenter` 换算位置，再沿经营给出的移动段做按帧插值。镜头外工人仍按经营秒推进；暂停停止插值和动画，不靠现实时间补进度。不同渲染帧率不得改变到达、播种、供水或收获。

可复用 `NpcCharacter` 的图集和朝向动画，但主地图实例不能再以预览的 180 像素/秒与 `MoveAndSlide` 自行推进位置。接入时要明确由快照驱动位置，并停止该实例的自主物理移动，保留独立预览的现有控制方式；任何动画完成回调都不能修改农田。

| 途中或浇水工作最后一秒降雨 | 当步雨水先满足需求，取消过期人工供水，生长不重置；湿田播种省去浇水。 |

| 三人开局与多人参与 | 经营状态及主地图确有 3 人；三块初始田被分别认领，多块待工田时三人都实际执行工作，不能只修改人数文字。 |
