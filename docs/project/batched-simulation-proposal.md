# 跨 tick 等价批量经营推进方案

关联 [#100](https://github.com/Fotally/Farm-Exchange/issues/100) 和 [#101](https://github.com/Fotally/Farm-Exchange/issues/101)，主计划为[参数化测试设计](developer-tools-parameterized-tests.md)。2026-10-06 已恢复实施，沿用已确认的一次跨过多个 tick 直接计算数据终态、事件 tick 按原顺序结算及统一工人位置公式。此前移出的草稿不作为验收成果，进度以主计划为准。

## 已确认约定

- 发布版 0.5×、1×、2×；开发版额外接受正整数倍率，默认提供 5×、10×、20×快捷项。
- 暂停和改速保留未完成 tick 的进度，暂停期间不累计时间。暂停时工人对齐真实经营位置；高倍率只呈现最新真实轨迹。
- 发布版支持的倍率同时按比例调整角色行走动画。开发额外高倍率下的动画沿用此前确认的正常播放速度，位置随经营进度变化。
- 当前局只有一个经营驱动；开发流程共用它，玩家手动改速中断整个流程。独立局只运行数据，不切换当前地图。
- 实施推进粒度改为批量数据计算；已选择跳到事件 tick 再按原顺序完整结算，密集成交保持逐笔结算。工人单 tick 与批量共用位置公式。

## 推荐：累计平静区间，结算真实事件

一次请求推进 N 个经营秒。协调模块找到最近业务事件：事件之前的平静区间用一次计算得到终态，在事件秒按同一经营规则结算，再计算下一段。循环数量取决于业务事件数量，而不是请求的 tick 数；不在批量入口内循环调用 `AdvanceTick()`。事件秒仍单独结算完整经营数据，同秒的多个事件一起遵循既有相位顺序。

请求覆盖已知没有外部输入的区间。现有降雨由调用方逐 tick 显式传入 `AdvanceTick(isRaining: true)`，不能被批量跨度跳过：调用方先批量推进到该输入 tick 之前，再通过保留的单 tick 入口执行雨 tick，随后请求下一无输入区间。该雨 tick 仍先供水再生长，使用相同经营规则；持续降雨时每个显式雨 tick 都是输入边界。当前主场景没有自动天气，方案不生成、预测或补充未来降雨，也不新增天气配置协议。

例如某个批次正在加工，距离完成还有 100 tick，且这段没有日期、工人、订单或测试边界事件。推进其中 80 tick 可以一次扣除 80×7 个精确时间单位并累计日历，保持库存不变；不扫描 80 次整张设施表，也不播放 80 次动画。距离完成只有 20 tick 时，一次请求 80 tick 则需先到第 20 tick 结算产出和领取，随后按新状态计算其余区间。

这里的“平静”允许剩余时间与移动位置连续变化，要求没有会改变后续规则或资源的离散事件。不能只因本秒没有收获，就认定之后都无事件。

| 模块与状态唯一拥有者 | 平静区间一次计算 | 需要精确停到的事件 |
| --- | --- | --- |
| `FarmingSystem` | 生长剩余精确单位减 7×N | 播种、供水、成熟、禁生促熟/清理、计划改变 |
| `ProcessingSystem` | 当前批次剩余单位减 7×N | 完工、领取、底线/库存/冻结变化、多场地竞争 |
| `WorkerScheduler` | 同一有效任务的移动进度与位置 | 任务选择/失效、抵达、播种/浇水、认领释放 |
| `GameCalendar` | 累计经营秒加 N，按既有整数比例查日期 | 其他模块实际需要处理的日界、季界和年界 |
| `CultivationPlanBook` | 保持不变安排，不反复同步 | 条起止、实际播种与结束、换季、年度凭据 |
| `MarketQuotes` | 跳过无公告/报价事件的日期 | 公告准备、正式报价、节日排期及其随机序列 |
| `TradeOrderBook` / `TradingService` | 依赖不变时省略重复的无成交检查 | 有成交机会、条件/资源/报价/季节变化、一次单终态 |

同秒结算继续遵循现有顺序：降雨 → 生长/加工完工 → 换季前临近成熟促成 → 空闲加工领取 → 工人动作 → 实际计划播种记录 → 日历、禁生清理与行情 → 年度表同步 → 订单。订单买入的原料仍在下一 tick 领取，不能因批量请求提前领取。

所有设施采用稳定锚点顺序，工人采用编号与现有轮转认领规则，订单采用创建顺序。批量调用期间不插入并发玩家命令；当前主线程在稳定检查点返回，后续输入按正常经营命令处理。

## 计算必须保留的口径

时间单位为每经营秒 7、每游戏日 360；日界按首次到达的整秒计算，一天可能为 51 或 52 tick。季节为 4320 tick，年度为 17280 tick。先核对 uint32 日历容量，超出不悄悄截断。

加工每批分别取整，不结转完工时超出的单位。例如萝卜加工为 180 单位，每批 26 tick，100 批加工占 2600 tick，不能对总单位取整成 2572 tick。买入后首次领取另外占第一个 tick；后续批次当秒产出后领取，从下一秒开始推进。多场地共享原料，不能各自拿同一库存独立计算产量。

工人选择任务的当秒可以移动，抵达当秒只移动，下秒才动作；干田播种和浇水分别占完整一秒。同秒无剩余时间转给下一任务。

当前工人位置使用每秒浮点加法。一次乘 N 与反复加法可能有微小舍入差异。已允许逐 tick 与批量统一使用“该段出发位置＋每秒位移×累计移动 tick”，到达时对齐工作中心。到达/动作时序及中途取消、换目标的边界必须单独对照，不能把差异一律当作显示误差。

行程的位移公式、当前段起点和累计移动 tick 留在 `WorkerScheduler` 内部。调用方只提交任务、请求推进和读取位置/活动快照；最近事件时刻也由工人模块给出，协调模块不推断直线距离或拼装移动公式。未来引入复杂路径时在工人模块替换行程实现并维持这些接口，本次不新增寻路算法、路径插件或假想的继承体系。

行情各次公告及报价仍依次结算，保持随机调用顺序、旧价递推和限幅。年度表不能只在最终日期同步：中途应实际执行的条、播种凭据和年度清理都要保留。

## 持续交易的成本与范围选择

若持续策略每 tick 都真实成交，这些 tick 都有业务事件。已选择首版精确逐次结算这些事件，仍直接累计它们之间的平静时段；不承诺任意经营状态都能以常数成本推进任意时长。

“稳定成交轮次聚合”暂不纳入本次：若将来另行设计，需在报价、季节、生产条件固定时，证明每轮各单的成交分支和数量稳定，计算第一次达到库存条件、现金保留或容量阈值的轮数，再一次提交这段净变化。必须检查每轮按订单顺序的资源前缀；即使整轮净变化为零，中间也可能超容量或不足。

聚合手续费必须是“单笔先向上取分，再乘轮数”，不能对合并货值只收一次取整费用；`LastFill` 保留最后一轮本单的单次数量与当时余额。这需要扩大交易模块设计与验证，不能在 `FarmGame` 复制交易公式。

## 最小接口与参数化流程接入

建议 `FarmGame` 提供一个批量推进入口：输入最大完整 tick 数，在真实事件及请求终点形成稳定检查点；返回实际 tick 数、宽整数收获/产出汇总和停止原因。检查点允许宿主终止本次请求。具体 C# 名称和类型在方案确认后确定，不先定义通用事件总线或继承体系。

各状态拥有模块封装最近事件和连续区间计算。`FarmGame` 只协调最近事件与同秒相位，不拥有第二份生产、工人或订单状态。单 tick 入口与批量入口共用规则和事件结算实现；测试可独立选择逐秒推进或批量切段来检查遗漏。

时间驱动持有倍率与半 tick 进度，按本次实际时间和倍率确定经营目标，再向同一批量入口提出请求。数据直接推进到下一个事件 tick，该 tick 按现有经营顺序完整结算，再定位下一段；处理范围由本次经营目标、业务事件和流程终止条件决定。画面按实际渲染帧读取最新真实状态，位置与动画按已确认倍率呈现。

参数文件无需改成步骤脚本。下一时间段终点、最后日期、剩余等待预算及下一业务条件，共同限制批量跨度：产品首次达到 Q 的那个完整 tick 停下检查并建单，本单从随后 tick 执行；中途改速或业务操作后重新计算下一段。末日期允许已有本单在该 tick 成交完成；若全流程仍未完成，则捕获终点并停止新操作。

一次跳过 N 个 tick，等待预算计 N。报告记录区间起止、实际推进数、真实事件和汇总，不能虚构 N 次逐 tick 观察。结束快照在稳定检查点捕获，落盘不重读现场。

## 实施依赖与验收

[#65](https://github.com/Fotally/Farm-Exchange/issues/65) 的绝对到期时间方向与本设计有关，但它只覆盖生产，不涵盖工人、计划、行情和订单。首版可在现有剩余时间状态上增加精确区间累计，不强制先建设时间轮或完成 #65；不得把本次进度标为已完成 #65。[#66](https://github.com/Fotally/Farm-Exchange/issues/66) 的全图索引优化仍是独立事项。

当前按 #100/#101 范围分配状态拥有模块、时间驱动/表现与固定流程。共用文件按所有权串行整合；主计划、根系统结构和公共索引由总工程师维护。开发完成后进行独立审查及指定引擎完整运行验收。

验收需要同种子、同命令、同终点的逐 tick / 批量对照，覆盖随机切段、七作物、同秒事件、无雨段与显式雨 tick 交替、日/季/年界、禁生严格阈值、计划条尾及冬春环绕、报价公告随机序列、冻结/底线、多场地竞争、订单顺序及逐笔费用、工人中途取消与换目标、测试预算恰好到期。比较公开状态与事件时刻，再继续推进后续事件，检查隐藏凭据、游标和随机状态是否一致。

性能检查需证明平静区间确实跳过逐秒执行，并分别记录平静和密集事件场景成本；不能只把多次方法调用包装成一次便宣称优化。完整代码交付仍需独立审查、逐模块80%覆盖率、指定引擎场景测试、1080P图形性能及Windows导出启动。

## 确认状态

事件拆段、密集成交逐笔结算、统一工人位置公式及行程实现留在工人模块内部均已确认。当前实施范围没有剩余待确认规则；若实现发现需要改变这些约定，先沟通再修改方案。
