## 测试流程固定，配置只提供数据

首个固定流程标识为 `buy-process-sell`，C# 维护以下步骤与检查：加载和验证参数→准备或绑定运行对象→记录基准→买入原料→观察加工→等待可用产品→创建一次卖单→等待本单完成→检查并报告。同一份步骤代码服务现场、独立局和现有测试调用。

配置改变商品、数量、目标场地、初始化种子、等待预算及时间速率方案，得到同一流程的不同测试用例。时间方案只指定连续经营时间段的倍率与最大推进终点，不改变买入加工卖出的步骤。配置不定义 `steps`、方法名、循环、脚本、反射类型或可关闭的断言。新增真正不同的操作次序或检查语义时，新增经过设计和审查的固定 C# 流程；加载不同文件不意味着能解释任意尚未实现的流程。

模块专用能力留在原模块；流程的参数验证、步骤和检查放在独立开发目录。一个具体流程、参数数据和运行上下文即可，不先建设插件注册、命令总线、表达式引擎或另一套测试框架。

| 共用内容 | 只随运行对象变化的部分 |
| --- | --- |
| 固定步骤、参数模型、正式经营命令、等待条件、检查定义和报告模型 | 如何取得FarmGame实例、准备测试条件、从哪里接收完整tick、能否做精确归因 |
| 同一个 `FarmGame` 和全部业务模块实现 | 当前局绑定已有对象；独立局创建显式种子的新对象 |
| 同一个流程的执行进度 | 现场观察Main的稳定经营检查点；独立数据局通过同一时间驱动受控推进公共经营入口 |

两种对象已接入同一固定流程，没有分别复制“现场版”和“测试版”。运行上下文只提供目标对象、推进/观察约定与证据范围；差异收在对象准备与驱动接入处，业务模块不按运行模式改变规则。实际接口见[参数化流程接口](../architecture/development/interface-parameterized-scenario.md)。

现场与独立模式已共用检查定义及开发窗口入口；受控条件不成立时，无法评估的检查明确记为“证据不足”，不能静默跳过并报全流程通过。现场已有库存、其他生产及同期操作的归因限制已在检查结果与报告中体现，独立局按受控条件执行严格检查。

## 共用时间能力的接入边界

发布0.5×、1×、2×与开发高倍率共用 `SimulationDriver`，由[#100](https://github.com/Fotally/Farm-Exchange/issues/100)实现；实际成员及计时约定见[共用时间驱动接口](../architecture/time/simulation-driver/interface-simulation-driver.md)。公共玩家能力保留在release；开发额外权限、测试时间方案和工具入口遵循开发排除策略。

固定测试流程提供日期目标与倍率意图，观察实际日期、速率和完整tick；当前局接入Main唯一经营驱动，独立局复用同一时间能力及FarmGame实现。流程不拥有计时器，不绕过暂停，不直接修改日历或分拆经营相位。每次操作后的UI、地图及工人表现由统一刷新路径协调。

现有纯tick测试仍可验证经营规则；带倍率的用例需要接入共用时间能力，不能忽略rate后声称按配置执行。速率本身的验证属于#100，开发流程只记录其请求与实际观察。

## 时间段使用游戏年月日

`execution.timePlan` 使用 `endDate` 与 `rate`：例如到游戏第1年4月1日前使用2×，随后到第1年7月1日前使用开发20×。倍率规则已确认：发布版仅0.5×、1×、2×，开发版另接受有限正整数倍率，默认提供5×、10×、20×快捷项；具体执行接口由#100实现。

日期采用已确认的 `yy-MM-dd`，例如 `01-04-01`。这里是游戏年、月、日；现有游戏每月28日，不按现实公历或System.DateTime判断日期。首段从本次流程准备完成后的实际游戏时点开始，后段从前一终点开始，终点严格递增。终点表示该日期起点，必须晚于流程基准；基准与所有区间在首条业务操作前核对，日期已过则明确拒绝，不自动改成相对日期或重置当前局。

流程在完整tick检查点观察首次到达或跨过目标日期，按下一段请求改速；不直接设置日期。最后一个日期限制本次测试的最大推进范围，步骤等待预算仍独立有效。业务流程提前完成即可结束；到最后日期仍未完成则报告时间范围耗尽。日期区间不改变固定业务步骤，不引入任意停止表达式或时间脚本。

停止条件控制本次测试及自动改速方案，不自动暂停玩家当前局。现场在终点捕获稳定检查点并结束测试，正常经营可以继续；报告使用已捕获快照，不在落盘时重读。独立局结束自身受控推进。共用驱动已提供检查点及推进限额，流程据此在完整经营边界观察和停止，不启动第二条现场经营循环。

## 首个流程的配置示例

以下是独立局用例的格式示意，不是已经存在的配置文件，也不设为默认参数：

```json
{
  "schemaVersion": 1,
  "caseId": "wheat-basic",
  "revision": 1,
  "flow": "buy-process-sell",
  "run": {
    "target": "independent",
    "seed": 12345
  },
  "execution": {
    "timePlan": [
      { "endDate": "01-04-01", "rate": 2.0 },
      { "endDate": "01-07-01", "rate": 20.0 }
    ]
  },
  "parameters": {
    "rawCommodity": "Wheat.Raw",
    "quantity": 1,
    "processorAnchor": { "x": 0, "y": 0 },
    "processingWaitLimitTicks": 1800,
    "orderWaitLimitTicks": 10
  }
}
```

现场用例将 `run.target` 改为 `current`，省略 `seed`，并将 `processorAnchor` 指向真实匹配场地。运行对象选择也属于配置数据，不会让“现场种子”改变已有游戏。报告引用实际加载配置的标识、版本和内容摘要，并记录已知实际种子；未知种子明确为空，不伪造复现能力。示例20×属于已确认的开发倍率，示例日期与数量仍不作为默认参数。

| 字段 | 现行约定 |
| --- | --- |
| `schemaVersion` / `flow` | 首版只识别约定版本与唯一固定流程；不认识就拒绝执行 |
| `caseId` / `revision` | 稳定用例标识与正整数配置修订号，用于长期保存和报告引用；不是脚本或程序集类型名 |
| `run.target` | `current` 或 `independent`，选择已有对象或新局夹具，不选择另一套经营实现 |
| `run.seed` | 独立局必填int32；现场不接受这个字段，避免误以为能重置现场随机过程 |
| `rawCommodity` | 七种合法原料之一；文本标识解析成现有 `CommodityId`，不是C#成员名或反射命令。买入加工品不符合本固定流程，直接拒绝配置 |
| `quantity` | 正整数份数；买入数量、目标产品可用量及一次卖单数量共用这个值，避免首版增加不必要的组合。交易容量/余额仍由正式命令重验 |
| `processorAnchor` | 整数基础格锚点；独立局按正式建造规则创建匹配场地，现场解析真实场地并核对匹配作物。地图和占用规则交给既有接口 |
| 两个等待预算 | 正整数经营tick数量，分别限制加工观察/等待与本单等待；不改变加工时长或市场排期，不把现实秒当经营秒 |
| `execution.timePlan` | 非空区间列表；`endDate`为有效的游戏日期字符串，终点严格递增且首个终点晚于流程基准。rate使用共用允许规则：发布版仅0.5、1、2；开发版另接受有限正整数倍率，快捷项为5、10、20；其他非整数倍率不接受。各区间仅改速，步骤仍固定 |

目标加工品根据所选原料的同一作物种类构造现有 `CommodityKind.Product` 标识，名称、加工定义等读现有目录；不让配置再填写可能矛盾的“产品”和“加工时长”。卖单固定为一次、Sell、Fixed、数量Q、预算None、金额保留0、商品总库存≥Q；费用和成交价格由真实模块决定。以后确有测试需求再增加参数，不先让整个订单编辑器都变为配置协议。

加载时严格拒绝未知/重复字段、缺失必填项、非法类型、要求整数的字段出现非整数、非法商品、非正数量/预算、未知版本/流程、非递增时间终点、非有限或未获当前构建允许的rate；rate可以为0.5，不能套用数量的整数限制。不忽略拼写错误、不自动换商品、不补隐藏默认值。所有区间先校验完，再操作现场；正式命令仍处理实际经营拒绝。配置错误、前置条件不足与业务拒绝分开报告。

同一文件执行多次时，流程结构相同；独立局还需相同种子、初始化准备和完整tick序列才具有受控复现条件。现场既有历史和同期输入仍会影响结果，不承诺仅靠配置重放完整现场。

每次启动只读取并校验一次配置，固定内存中的本次执行参数；运行中不热加载文件或用窗口草稿覆盖。不创建配置副本文件，也不把完整配置嵌入报告。文件修改下次启动生效；报告记录加载时的原文件引用及内容摘要，避免参数漂移。

## Q份买入→加工→卖出的固定步骤

| 固定阶段 | 公共执行与检查 | 独立局 / 现场的证据范围 |
| --- | --- | --- |
| 准备与基准 | 验证参数、目标对象与加工匹配；记录资金、库存、底线、场地、订单、日历和行情 | 独立局通过正式接口移除赠送设施并建造唯一目标加工场，设置原料底线0，确认无其他生产/订单。现场只绑定和检查，不自动拆除、撤单或改底线 |
| 买入Q份 | 调用真实 `game.Buy(raw, Q)`；检查Success、实际数量及命令边界的资金/库存前后关系 | 两种模式都能比较这次同步命令的结果。拒绝就停止后续操作并记录真实原因，不赠钱补库存让流程继续 |
| 观察加工 | 记录目标加工状态与剩余秒，等待出现加工状态 | 新独立局先完整推进到领取，买入后不提前调用加工模块。现场保留已有批次和正常领取时点；已在加工也记录为真实状态，不声称由本次买入启动 |
| 等待产品 | 在完整经营检查点查询目标产品的可用量，达到Q才进入建单；记录Produced汇总与目标场地快照 | 独立局唯一场地、无干扰，能验证Q份实际加工与库存关系；现场达到Q不证明这些产品全部来自本次购买或目标场地 |
| 创建一次卖单 | 通过 `CreateTradeOrder()` 提交固定卖单，记录返回ID、Request、Waiting、该单冻结和当前库存 | 紧邻建单前后同步快照检查Q份冻结及可用量变化，不要求全局库存从0开始。条件是总库存≥Q，冻结后仍按真实条件执行 |
| 等待本单成交 | 按ID观察Status、LastFill、冻结归属；等待未暂停完整tick中的真实Execute，不手工调用订单内部执行 | 同期玩家操作撤销、改动本单或导致无法成交时，报告实际结果；不自动恢复旧配置或再次建单 |
| 检查与报告 | 真实LastFill商品/方向/数量应符合本次请求，本单完成后冻结归零；验证总量＝可用＋冻结等可观察关系 | 独立局能核对成交前后余额净增＝TotalCents－FeeCents。现场其他订单或输入会改全局余额，精确归因检查证据不足时单独标记，不以最终余额不等直接归咎本单 |

`quantity` 不限于1：独立局加工领取初次消耗一份，后续完整tick逐批完成并继续领取；流程等待目标产品可用量达到Q，而不是仍沿用“一秒Produced必须是Q”或“第一次产出就停止”的旧示例断言。加工数量、时长与重新领取均由真实算法执行，工具不计算另一套批次模拟。终点检查原料/产品及场地状态须使用受控条件与真实结果，不写死为一份。

现场检查使用相同定义，但精确生产归因和整段资金守恒需要足够证据。当前没有逐实例产出事件、加工批次凭据、完整交易历史或每单库存前后结算快照；不能声称这些已有。首版可报告“执行完成，可观察检查通过，部分归因证据不足”，整体不能写成严格测试全通过。若要求现场也做同等级精确检查，需另行确认最小诊断事件或结算快照，不能复制业务计算来补证据。

等待预算按实际已完成经营tick计数，倍率只改变实际等待时间。当前局暂停时自动加工/订单及时间方案同样暂停，界面等待玩家继续或中止，不偷偷解除暂停；真实拒绝、中止、超限、时间范围耗尽、检查失败及证据不足分别记录。恢复后由Main唯一驱动通知流程下一检查点；不另起tick循环，不冻结其他经营输入。

加工预算从买入后第一个完整tick开始计数，观察加工与等待Q份产品共用一个预算，不在两个阶段分别重置；订单预算从建单后的第一个完整tick开始计数。所有计数都基于已完成tick，零次推进的暂停期间不消耗经营tick预算，也不阻塞窗口的继续/中止输入。预算值由文件提供，示例数值不是已确认默认。

独立局由运行上下文准备暂停对象，开始后使用自身 `SimulationDriver` 并在稳定经营检查点观察流程进度；完成、中止或异常退出后结束该独立对象的受控推进。首版独立局只运行数据，不绑定或切换当前地图。现场复用Main唯一驱动并始终服从玩家暂停/继续状态，不套用独立局的启动控制。

## 现场操作就按玩家真实操作处理

按用户本轮要求，不采用旧稿“运行流程期间统一屏蔽其他经营写入”的建议。测试工具提交的买入、建单等命令与玩家操作一样，遵守当前资金、库存、底线、冻结、场地和暂停状态；场景不享有免费操作、强制成功、自动撤销他单或资源回滚。

其他玩家输入照常进入Main和经营模块；命令及tick在既有主线程执行路径上顺序处理，不把测试流程的等待变成锁住现场。每条自动操作后走统一刷新路径，用户的暂停/继续/编辑或撤单结果保留并写入观察报告。首版不为这一需求先建设完整玩家输入录像系统；无法观测的同期操作和生产归属明确列为证据限制。

现场时间方案由玩家启动，相当于授权按区间提交改速；它不会绕过暂停。已确认玩家主动改速即中断整个自动流程：停止后续业务操作、自动改速请求、等待和流程检查，不只停止变速计划。保留玩家选择，不自动恢复旧倍率或自动续跑；已发生的买入、建单和生产变化不回滚，当前游戏按正常玩家经营继续，已建订单仍由真实订单规则处理。

中断收尾仅记录原因、步骤、相关tick和中断检查点快照并输出JSON；保留中断前已有结果，后续检查标为未执行，不报全流程通过，也不把玩家改速视为驱动缺陷。改速来源由共用驱动的 `RateChanged` 通知区分 `Player` 与 `Scenario`，窗口订阅玩家来源并中止现场流程。

流程宿主通知、暂停后工人位置同步属于本次接入范围。本固定流程不要求现场暂停单步，正常玩家暂停语义已经足以描述其等待；若后续另选单步工具，再设计完整暂停协调入口。

## 配置、源码、文档与报告分开

实施目录如下：

```text
scripts/development/scenarios/         固定测试流程C#源码
tests/scenario-configs/buy-process-sell/  受版本管理的JSON用例参数
docs/project/                         设计、字段语义和使用说明
build/test-runs/<run-id>/              编辑器/仓库内执行产生的报告
```

参数文件属于测试数据，不放在 `docs/`，报告不放在 `scripts/` 或 `tests/`。测试数据目录和编译排除规则由 #101 落地。现有 `.gitignore` 已排除整个 `build/`，因此仓库运行报告自然作为运行产物保存，不混入源码提交。

已按暂定报告约定实施：编辑器/仓库运行使用项目根目录 `build/test-runs/<run-id>/`，本地dev导出包使用包外侧 `reports/test-runs/<run-id>/`。Windows定位exe所在目录；macOS定位 `.app` 父目录，不写入Contents或程序集目录；不依赖启动工作目录或Godot引擎安装目录。Windows真实包、根目录解析及可写性检查已验收；macOS路径已有夹具验证，原生包验收未在本次Windows环境运行。显式选择输出根目录的入口仍在首版范围外，不静默换路径。

输出位置按上述包位置规则解析，与流程JSON参数分开。首次执行前检查输出位置可写；写入失败向界面/现有测试入口明确反馈，保留已有执行结果，不伪装报告已落盘或换路径继续。首版没有输出设置界面。

配置长期保存在测试数据目录或用户选择的配置库中，编辑器和dev包都加载这些持久文件，不在每次运行或报告目录复制。现有预设排除tests资源，不能声称配置会自动随包导出；若以后需要开发包分发配置，应另行设计明确版本的发布需求，当前不默认复制。release排除流程源码、开发额外倍率入口、配置与专用资源，但保留公共0.5/1/2速率能力；CI继续不生成dev包。

## 报告先只输出JSON

每次执行的唯一run-id目录先只包含：

```text
report.json          结构化执行结果、检查证据及配置引用
```

JSON保存字段类型、单位和缺失值，独立存放在报告目录；不生成Markdown摘要。已按暂定路径与JSON单一输出约定实施，仅生成 report.json，不生成config-used或其他配置副本。

报告延续[已有字段建议](developer-tools-cross-module-debugging.md#自动调试报告及分析边界)，补充配置引用、流程版本、运行对象、初始化、配置校验结果、请求/实际倍率与变速来源、暂停和tick序列、操作返回值、检查证据、快照和失败位置。真实操作参数属于执行记录，可保留；报告不再次存整份配置。LastFill无成交tick时记录首次观察到的tick，不伪造内部时间戳。

当前JSON配置引用保存caseId、revision、原文件位置和加载时原始UTF-8文件字节的SHA-256。稳定ID或路径本身不能证明当时内容，内容摘要用于核验，不能从摘要还原文件。Git提交引用保留为后续选项，首版不记录或推测配置所属提交。

为积累可复现用例，建议修改已使用配置时新增修订并保留旧文件，不覆写历史版本。加载时以实际内容计算摘要，不信任文件里自报的摘要；运行后原文件变化不改变已加载参数，后续查报告若引用缺失或摘要不符，明确标为历史配置不可核验，不用当前文件冒充旧输入，也不因此自动补副本。

检查结果区分通过、失败、证据不足、未执行；流程结果还区分操作拒绝、等待超限、时间范围耗尽、中止、完成但证据不足、配置或输出错误。用户已确认现场可有证据不足，独立局严格检查；所有必需检查可评估且通过才给出严格通过。自动执行结束、自动检查通过、根因定位分开，未知或无法归因不算通过。
