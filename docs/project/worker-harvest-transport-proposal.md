# 工人采收与搬运设计提案

关联 [#112](https://github.com/Fotally/Farm-Exchange/issues/112)，归属 [#105](https://github.com/Fotally/Farm-Exchange/issues/105)。2026-10-07 核对源码与清亮 v2 动作。以下新增玩法均待用户确认；当前继续自动收获入公共库存，首批产出 FX 不代表已实现工人采收或搬运。

## 事实、选项与建议分期

现行 `FarmingSystem.AdvanceGrowth` 达到成熟目标后清除本轮，`FarmGame.CollectHarvest` 一次增加公共库存并通知年度表结束；禁生换季促熟共用该路径。`Inventory` 拥有可交易原料、加工品、冻结量和加工保留线，`ProcessingSystem` 自动领取可用且超过底线的一份原料。没有成熟待收、地面货物、运输目的地或携带容量。[作物规则](../gameplay/production/crop-growth.md)、[加工规则](../gameplay/production/processing.md)和[库存交易](../gameplay/trading/sales.md)是当前生效基准。

| 选择 | 新增经营含义 | 素材范围 |
| --- | --- | --- |
| A：保持自动结算 | 无新增劳动和物流状态，真实产出后只显示 FX | #108 产出表现；harvest/carry 保留 |
| B：人工采收后直接入库 | 成熟待采收占田，工人到场采收后入公共库存 | 真正适配七作物的采收动作与工具，不启用 carry |
| C：采收并搬至交货点 | B 加携带与交货，直到卸货才可交易/加工 | harvest、carry_idle、carry_walk、交货点及七品类道具 |

建议若要增加劳动，先选 B，确认采收对节奏的影响后再评估 C；它减少运输目的地和容量尚未明确时的猜测。此建议不表示用户已同意更改自动收获。C 的必要设计约束在下文完整列出，不能为播放箱子动作自动启用物流。

## B 的建议规则与唯一归属

`FarmingSystem` 唯一拥有新增成熟待采收阶段、成熟数量以及作物轮次凭据；`WorkerScheduler` 继续唯一拥有工人位置、任务、实例独占认领与进度；`Inventory` 只在采收成功后拥有本批可交易数量。人物表现只读取快照和成功结果。

建议成熟后保留到跨季、停止自动复种；采收成功才结束本轮、清水并启动年度表后续判断。立即改种或拆除沿用丢弃田内未入库作物的含义，并明确提示成熟数量损失；预备下一轮和年度表编辑保留本轮待采收。成熟保护及上述接管行为需用户确认，不能沿用当前换季“未成熟清除”代码却把成熟也清掉。

建议采收任务复用现有独占认领：同田只允许一人，执行时重验实例、作物轮次和阶段；成功只一次。工人数继续为三人，移动仍每秒 3 格，播种/浇水各 1 秒。采收耗时与任务优先级**不在此定值**，必须先确认并测量三人与 24 田场景，不能以加速人物或隐藏增员保持旧预算。

拟定最小 Interface：`FarmingSystem.GetWorkNeed` 提供带凭据的采收需要；经营入口中的完整 `TryCompleteHarvest(request)` 在同一执行路径内重验作物、检查目标库存容量、清除田内数量、入库并通知年度表，返回真实结果。失败时田和库存均不改变，不让 UI 或动画分别调用“清田”和“加货”。这条内部 Seam 由真实调度调用，测试通过经营步进与只读快照验证。暂停不消耗任务时间；恢复重验凭据，高倍率批量推进必须在采收完成与换季事件处分段。

若公共库存容量不足，建议保持成熟作物且显示等待容量，不丢货、不越界；任务释放后仅在相关库存变化时重新成为可执行需要，避免每秒反复采收。容量不足行为也需确认。

## C 的货物归属与完整转移

C 必须先决定交货点的位置、是否可拆、建造费用、每次携带容量以及卸货耗时。本提案建议固定不可拆的公共交货点、每趟单一作物；这是供讨论的最小运输方案，不是新增仓库规则。目的地不能暗中用任一加工场地替代，否则买入原料、加工保留线和冻结含义都会改变。

若选 C，建议新建实际拥有运输货物的 `HarvestCargo` Module，唯一持有工人携带的作物、数量和来源凭据；`WorkerScheduler` 只保存任务与货物引用，`Inventory` 不把在途货物计入总量或可用量。田内待收数量仍归 `FarmingSystem`。本方案不增加地面掉落：工人取消或切换岗位时保留货物，先交货再接新任务；工人删除功能本来未实现，若与 #43 一起引入须另定携货人员退出约定。

资源流转为“田内成熟数量 → 工人携带数量 → 公共库存 → 加工投入”。每个箭头通过一次完整命令转移；禁止各 Module、动画和背包 UI 同时保存同一份货量。`FarmGame` 暴露/协调 `TryCollectToCargo(request)` 与 `TryDeliverCargo(worker)` 这样的完整结果，私有转移过程先做全部检查，再提交两端变更。满载则剩余成熟量留田，最后一批采收后才通知年度表本轮结束，避免同一轮重复计算产量。

| 情况 | C 的建议处理，均需规则确认 |
| --- | --- |
| 出发前目标田拆除或改种 | 原任务凭据失效；未采货按相应丢弃规则处理，携带量为零 |
| 已采后田拆除或改种 | 已携带货物保持，来源田不再拥有它；交货仍有效 |
| 卸货时库存满 | 原货物全部留在携带状态，显示等待，不部分提交、不销毁 |
| 携货时切任务 | 暂不执行新生产任务，先完成交货；不清空携货状态 |
| 买入、卖出、冻结、加工底线变化 | 只作用于公共库存；在途不能出售、冻结或被加工领取，卸货后再按正常规则参与 |
| 暂停、改速、取消视觉效果 | 暂停冻结任务；改速保留业务进度；动画取消不转移或丢弃资源 |

完整守恒口径为成熟待收量+携带量+公共原料+已投入原料，结合实际收获、出售、加工转换及经确认的改种/拆除损失记录核对。不能只比较库存前后值，因为投入和运输本来会移出库存。

## 实际动作与图片层级

包根 `default/npcs/catalog.json` 列 20 人；各角色的 `animations.json`、合成 PNG 和 SpriteFrames 定义动作。抽查 npc001：harvest 每方向 8 帧、参考一轮 1.16 秒、镰刀，道具击中帧 3/4；carry_idle 8 帧、2 秒，carry_walk 6 帧、0.75 秒，使用箱子。这些是视觉参考时长和事件，不能决定业务耗时或触发加货。

三动作均为 64×64，脚根 `(32,60)`，四行 `down/left/up/right`；右向已烘焙镜像，不再二次翻转。合成帧已经包含身体、可见道具与可见 FX，不重复叠加同一工具。人物按真实脚根和建筑/植株接触点统一排序；箱子随合成帧，不用全局最高层强压田或墙。

| 作物 | 现有镰刀适配判断 | 正式启用所需素材确认 |
| --- | --- | --- |
| 小麦、水稻 | 割取方向有语义基础，但接触点和株高仍需实测 | 镰刀四向接触、收获前后植株变化 |
| 玉米 | 通用挥镰不等于采穗 | 采穗动作或明确认可整株收割含义 |
| 马铃薯、萝卜 | 需要挖/拔，现有镰刀不匹配 | 挖掘或拔取动作及根部接触 |
| 向日葵 | 不能从通用挥镰断定为采盘 | 采盘/割茎语义、株高和工具 |
| 甘蔗 | 切割有基础，通用镰刀接触并未验证 | 茎基部切割、长束携带或容器适配 |

箱子可以表示容器，但不能声称已提供七作物专用货物。B 不引入箱子；C 需确认统一封闭容器或逐作物道具，既有草束/工具层只按实际文件验证，不能用名字猜用途。所有新增素材遵守[素材管理](asset-organization.md)与[来源说明](../research/bright-complete-v2.md)。

## 依赖与验收范围

[#38](https://github.com/Fotally/Farm-Exchange/issues/38) 现行越季清除不含成熟待采；新增阶段必须同步生长预测、年度表结束和换季促熟，不能只改 WorkerActivity。[#35](https://github.com/Fotally/Farm-Exchange/issues/35) 管加工领取与底线；C 不绕过其库存入口。[#43](https://github.com/Fotally/Farm-Exchange/issues/43) 管人力扩充，不为此提前增加工人数。[加工岗位提案](worker-processing-proposal.md) 若一起实施须共同确认任务优先级。

确认后的可执行用例：成熟恰逢换季及促熟进入待采；三人同时争一田只采一次；改种/拆除失效；已携货来源拆除；卸货容量不足后恢复；卖单冻结与底线；批量/逐秒等价；暂停和改速；年度表跨季不重复播种；24 田新增任务等待与原两日指标变化。图形至少 1920×1080，逐作物四向检查工具、箱子及前后遮挡。功能及动作素材共同完成后执行独立审查、模块覆盖率和引擎导出验收。

待用户决策：A/B/C；成熟保护与改种损失；采收耗时及调度优先级；是否认可原预算变化；C 的交货点、容量、卸货与满库规则；七作物动作和携带外观。未确认前只完成本设计，不新增业务状态。
