# 游戏测试分类调研

本调研用于组织当前 Windows 版《Farm Exchange》的测试。分类是项目的测试安排，不表示 Godot 要求项目采用某一种测试框架。现阶段只覆盖已实现的 128×128 地图、六种作物及加工、交易和镜头交互；存档和离线收益尚未确定，待实现后再补测试。

## 资料依据与分类

Unity 的官方测试框架区分无需启动游戏的 Edit Mode 测试与运行时的 Play Mode 测试，并提供扩展框架来收集性能测试结果。Godot 也在引擎开发中使用单元测试和集成测试。这些资料支持按测试目标分层；本项目继续使用现有 Godot C# 场景测试，不引入 Unity 工具。[Unity 测试框架](https://docs.unity3d.com/6000.0/Documentation/Manual/com.unity.test-framework.html)、[Unity 性能测试 API](https://docs.unity3d.com/6000.0/Documentation/Manual/com.unity.test-framework.performance.html)、[Godot 单元测试](https://docs.godotengine.org/en/4.7/engine_details/architecture/unit_testing.html)

| 类别 | 本项目要回答的问题 | 目前对应内容与建议组织方式 | 执行方式 |
| --- | --- | --- | --- |
| 规则单元测试 | 单条经营规则和价格函数是否正确？ | `TestFarmGame` 中的价格、种植、加工、库存、交易、购地边界检查；由 `TestSuite` 单独标记。 | 自动化，每次提交运行。 |
| 场景集成测试 | 游戏状态、地图和界面连接后是否仍能完成操作？ | `TestWorldMap` 检查坐标、选择和镜头边界；`TestMainScene` 检查实际按钮及状态更新。 | 自动化，每次提交运行。 |
| 全流程与冒烟测试 | 玩家是否能从启动游戏走通生产、加工、出售、购地？构建产物能否启动？ | 在现有主场景检查上明确一条核心循环路径；Windows Release 导出后启动程序并检查退出码，人工按《构建与验收》的玩法步骤验收。 | 核心路径与启动自动化；视觉和操作体验人工检查。 |
| 性能与压力测试 | 16,384 格均有已实现实体时，逻辑能否持续运行、画面实际能有多少 FPS？ | `TestFarmGame` 的满地图检查每次运行；`TestPerformance` 的有窗口 FPS 压测按需运行并写入报告。 | 逻辑检查每次自动化；图形压测在相关修改或建立基线时运行。 |
| 兼容性测试 | 游戏在目标 Windows 环境、分辨率和图形硬件上能否正确启动与显示？ | 保留 Windows x86_64 导出启动检查；在有代表性的分辨率和硬件上核对界面、输入、帧率。项目尚无其他平台承诺。 | 可自动化启动；不同硬件上的画面和输入人工验收。 |
| 可用性与无障碍体验测试 | 玩家能否看清格子和经营信息、理解操作、顺利使用鼠标与键盘？ | 邀请玩家走一遍核心循环，观察卡点；检查文字可读性、缩放、格子选择和键盘移动。 | 人工试玩并记录问题；有明确规则后再补可自动化的检查。 |

微软的游戏认证资料把构建稳定性、进入游戏与菜单、不同 PC 配置列为实际测试内容；其无障碍测试服务同时覆盖核心功能路径与玩家反馈。这支持将「程序启动」和「玩家能顺利操作」分别验收。[Xbox 游戏认证测试](https://learn.microsoft.com/en-us/gaming/gdk/docs/store/policies/console/console-certification-requirements-and-tests)、[微软游戏无障碍测试](https://learn.microsoft.com/en-us/gaming/game-publishing/concepts/certification/certification-mgats)

## 满地图性能测试口径

**负载定义。**地图总计 `128 × 128 = 16,384` 格。「每格有实体」以本项目已经实现的农田和加工场地为准；测试配置包含 8,192 块农田与 8,192 处加工场地，六种作物在两类建筑中均出现，并保持游戏原本只有一名工人的规则。测试场景走正式游戏的状态更新及地图绘制路径。记录建筑数量、绘制循环实际处理的地块数与推进的 tick 数。绘制循环的候选地块可能包含视窗外的格子，因此不能把报告里的“绘制地块数”当作“屏幕可见格数”；也不能把 16,384 个格子全在屏幕上同时可见等同于 16,384 个实体存在于世界状态。

**两种测量分开。**必跑的无窗口场景测试核对每格状态及六种农田与加工场地，然后推进 50 tick 并报告耗时；它不能报告真实渲染 FPS。Godot 4.7 明确指出，headless 模式下 `Engine.get_frames_drawn()` 始终返回 `0`。[Godot `Engine` 类](https://docs.godotengine.org/en/4.7/classes/class_engine.html)

**真实 FPS 的步骤。**当前测试使用项目指定的 Godot 编辑器 Debug 运行时和有窗口的主场景，生成满地图状态后预热 2 秒、采样 8 秒；窗口为 1280×720、镜头为 1.25 倍缩放并水平往返移动，同时按主场景计时器推进 tick。报告记录绘制帧数、平均 FPS、帧耗时中位数、P95 与 P99、硬件和渲染条件。它测的是当前开发构建的移动镜头负载，不能直接当作 Windows Release 成品或静止镜头帧率。Godot 的 `Performance.TIME_FPS` 每秒更新一次，`TIME_PROCESS` 提供单帧处理耗时；这些监视器和帧时间分析可辅助定位，但某些监视器在 Release 中返回 `0`，使用前要核对。[Godot `Performance` 类](https://docs.godotengine.org/en/4.7/classes/class_performance.html)、[Godot 分析器](https://docs.godotengine.org/en/4.7/tutorials/scripting/debug/the_profiler.html)

**比较条件。**记录 CPU、GPU、内存、Windows 版本、Godot/游戏构建、分辨率、显示刷新率、VSync、FPS 上限、窗口或全屏模式。VSync 可以把 FPS 限制在显示器刷新率，`Engine.max_fps = 0` 才表示没有显式 FPS 上限；不记载这些条件时，单个 FPS 数字不能用于比较机器或提交。[Godot `Engine` 类](https://docs.godotengine.org/en/4.7/classes/class_engine.html)

目前没有经用户确认的目标硬件或最低 FPS 数值。每次自动化运行满地图逻辑检查；修改地图绘制、镜头、实体数量或渲染设置，以及需要建立性能基线时，再运行图形压测并保存报告。性能门槛应在确定目标硬件并形成基线后再制定。Godot 官方分析器目前不支持对 C# 脚本逐函数分析；如果帧率异常，可用它查看整体帧时间，再用支持 Godot 的 C# 分析工具定位脚本耗时。[Godot 分析器](https://docs.godotengine.org/en/4.7/tutorials/scripting/debug/the_profiler.html)
