## 能力归属与流程组织是两件事

模块专用能力仍属于维护该状态和规则的原模块：交易结算由交易模块负责，库存与冻结由库存模块负责，加工批次由加工模块负责，日历由时间模块负责。`FarmGame` 协调跨模块经营操作、执行固定 tick 相位并聚合必要快照。开发专用 partial 文件只是给同一个模块补充源码，不自动提供事务、联动或一致性保证。

开发调试场景负责一个可重复执行的检查流程：准备前置条件、串联真实操作、请求推进或等待、比较观察结果并形成报告。流程可以同时涉及交易、库存、加工、时间和订单，因此放在独立的开发调试目录，不要求归属于某个业务模块。它只持有本次执行的步骤、输入、基准快照和报告，不拥有另一份经营状态。

这里的“场景”是检查流程的含义，可先是具体 C# 类，不预设新建 Godot `.tscn`。当前只用一个流程检验分工，不先建通用脚本语言、命令总线、插件、测试框架或复杂调度器。

| 模块 / 角色 | 维护的状态与职责 | 调用约定 |
| --- | --- | --- |
| 原业务模块 | 真实库存、资金、加工、订单、日期等状态，完整业务规则 | 不因工具调用而改用另一套经营算法 |
| `FarmGame` | 协调经营命令和完整 tick；提供只读经营快照 | 必要的开发专用操作仍封装完整业务影响，不加入场景步骤、断言或报告生成 |
| 开发调试场景 | 本次流程的准备、操作次序、等待条件、检查与报告 | 使用 `FarmGame` 接口，向统一驱动请求推进；不直接访问或改写业务容器 |
| 工具窗口 | 启动参数、进度、检查结果与报告展示 | 发出启动/中止意图，不执行经营算法，也不承载全部流程代码 |
| `Main` | 绑定运行对象、接入唯一经营驱动、协调推进和画面刷新 | 调度当前流程何时可继续；不编写具体流程的业务断言 |

```text

  gameplay/development/FarmGame.cs              模块专用经营入口，按需存在
  ui/development/DeveloperToolsWindow.cs         启动与展示，按需存在
  development/
    scenarios/RawProcessingOrderScenario.cs     本文唯一候选跨模块流程
    DebugScenarioReport.cs                      本次流程的报告数据，按需存在
```

以上是候选名称与目录，不代表已建立文件、类或接口。`scripts/development/` 可使用 `FarmExchange.Development` 命名空间，实施时才同步目录规范与静态检查映射；模块专用 partial 文件仍使用原模块 namespace。一个具体流程加报告数据即可讨论本例，无须先定义 `IDebugScenario`、插件注册或通用命令枚举。

两类开发源码都遵循[C# 组织讨论](developer-tools-csharp-organization.md)的编译范围：模块内 `development/` 与独立 `scripts/development/` 均由候选 `scripts/**/development/**/*.cs` 规则覆盖；引用它们的公共组装代码需相应条件编译。开发专用资源由导出预设排除，共享场景不能引用 release 不存在的脚本。本轮不写入这些配置。

## 操作必须履行完整执行路径

每个专用入口在选定功能后，应明确输入、执行时点、关联模块影响、失败是否零修改、返回结果与需刷新的表现。能调用某个原模块方法，不等于已经履行其所有经营联动。

- 当前正式 `Buy()` 完成结算与入库，已有闲置加工场在下一次完整 tick 的领取相位领取；如果入库后新建加工场，建造入口会立即执行全场闲置加工领取，不只是新场地。自动订单买入在 tick 尾部，仍晚于本 tick 加工领取，不能工具买入后自行提前调用领取。
- 开发原料注入尚未实现，也没有确认领取时点。若以后选择此能力，必须先定义它是等待下一 tick，还是在经营入口内封装即时领取；不能只调用 `Inventory.Add` 后宣称全部联动已完成，更不能冒充正常买入。
- 时间推进调用完整 `FarmGame.AdvanceTick()`：生长与加工入库、换季临界促熟、加工领取、工人、实际计划播种记录、日历/换季清理/行情、计划同步和订单执行保持原路径。不得直接改累计秒数、剩余加工时间、产品库存或订单状态来达到检查目标。
- 暂停门禁存在于 `FarmGame`、工人和日历。现场流程服从玩家暂停状态；单步仍是未选择的候选工具，本文不设计其时间接口，也不能用绕过门禁来实现流程推进。

具体步骤读出的返回值和快照是检查依据；流程不自己计算一套行情、加工增长、费用取整或自动交易条件。库存与资金的前后守恒关系属于可观察检查，可以使用真实结算结果验证。

## 当前游戏与独立调试局

| 运行对象 | 适用场景 | 状态影响与限制 |
| --- | --- | --- |
| 当前游戏现场 | 检查当前设施、计划、冻结资源及特定操作的真实联动 | 修改作用于玩家当前局；时间推进会让其他设施、计划、行情和订单一起执行。开始前记录基准并验证条件，不自动拆除现有设施、清空资源或撤销订单来造出纯净局 |
| 独立调试局 | 固定种子和受控初始条件下复现完整流程 | 创建同一个 `FarmGame(seed)` 实现，状态与当前局分离；准备时也使用正式接口。它不是另一套模拟器；两种对象共用流程进行设计，不意味着已有运行中换局或双局画面绑定能力 |

当前局已有历史，仅固定种子不能复现历史状态；目前无完整存档/恢复，也未公开实际随机种子。不能报告“已完整复现现场”，不能承诺中止后自动回滚。现场中止只结束自动流程、释放其控制，不改变玩家暂停状态；手动改速中断时保留玩家刚选择的速度，不恢复旧倍率、不续跑自动步骤，游戏按正常经营继续。已经发生的建造、交易和生产变化保留并报告，独立局则结束自身受控推进。

独立局示例可用明确传入的种子；准备阶段的拆除、建造、底线设置也必须记录，不能只记录后半段买卖。现有纯tick规则测试可受控调用公共 `AdvanceTick()`；新增包含速率参数的测试还须复用共用速率驱动，不能忽略倍率后声称完整按配置执行。画面或当前局通过唯一场景驱动推进，独立对象不授权当前局另起循环。

按用户后续意见，两种对象共用固定流程、参数和报告，差异限于对象准备、推进接入和证据范围，考虑一起纳入后续范围；本轮只共同设计，不复制两套流程，不将此解释为实施授权。具体字段与接口以参数化设计讨论为准，不先建复杂驱动框架。

## 统一驱动与刷新

建议先以一个具体流程保存“当前步骤、等待条件、已推进次数”。流程完成一次操作后返回进度；需要经营秒时提交推进请求，由 `Main` 协调的唯一驱动通过经营入口执行完整 tick，完成刷新后再让流程检查下一步。`AdvanceTick()` 必须在非暂停状态调用；若选择现场保持暂停的单步体验，需先补齐完整暂停协调入口，不能假设暂停调用仍能推进。当前局运行期间，普通计时器不能额外推进，工具不能另起后台计时器、线程或独立 `for` 循环推进同一个游戏。

检查在命令结束或完整 tick 结束的稳定检查点读取快照。按用户后续意见，当前局操作与玩家正常操作同等处理，不因流程等待封锁其他经营写入；撤回前轮屏蔽输入的建议。同期输入和其他生产的影响按实际结果记录，不能保证所有关系都可精确归因。等待以真实完整tick或画面帧为依据，不以现实秒代替经营步数，也不直接推进某个模块。

操作与 tick 后复用统一刷新路径：UI 显示真实库存、资金和订单；地图根据经营变化同步；工人表现读取同一对象的新快照。现有 `Main.RefreshAfterGameChange()` 已统一地图与 UI，但它是私有方法，没有公开的流程接入。`WorkerPresentation._Process()` 在暂停时先返回，若以后实现暂停单步，需明确补充暂停后的快照位置同步；不能把 UI 更新等同于工人画面已更新。

## 用一个跨模块案例检验分工

下面采用Q＝1受控独立局解释检查关系；用户已选择该流程方向，但数量和商品应参数化，具体模型见参数化设计，未授权实现。当前局检查可观察关系并执行真实操作；不满足受控条件时，只将相应精确归因检查记为证据不足，不自动重置现场，也不因存在其他设施而拒绝全部正常操作。

目标：购买一份小麦原料，使用一个小麦加工场完成一批，创建一次固定数量卖单并成交。品种和数量仅作为本文案例输入；不新增经营数值规则。

受控准备条件：显式种子新局，暂停；通过 `GetBuildingSpaces()` 与 `RemoveBuilding()` 移除赠送设施，再通过 `TryPlace()` 建造唯一匹配加工场，设置原料加工底线为零。逐次检查命令结果，读取基准确认无农田、无其他加工场/订单、目标原料和产品总量/冻结均为零，且可用资金足够。清理仅用于独立局；现场保留既有场地、底线和历史，使用实际命令结果检查。准备失败不能用赠送资源、直接写状态或跳过检查继续。

本例的暂停和推进约定必须显式记录：准备、买入、建单及检查点保持暂停。在没有活动 Main 计时器的独立数据夹具中，受控驱动每次推进按现有公开入口执行 `game.SetPaused(false)` → `game.AdvanceTick()` → `game.SetPaused(true)`，在异常退出路径也恢复暂停；逐次记录暂停命令与实际 tick。只有真实完成 tick 后才能进入下一检查步骤。这复用完整经营路径，既不绕过任何暂停门禁，也不将各业务相位拆开执行；场景只提出推进请求，不在步骤内部另起循环。

该独立数据夹具仅说明当前纯tick测试入口，不设计新增时间接口，也不意味着当前Main已有同样的单步接入。带日期/倍率的流程依赖#100共用时间能力；现场按玩家暂停/继续状态等待，画面绑定必须接入唯一驱动。暂停单步仍是未选择候选能力，不把它当作首流程的前置要求或现成功能。

| 步骤 | 谁执行 / 从哪里进入 | 读什么、如何检查 |
| --- | --- | --- |
| 启动并准备 | 窗口发启动意图；`Main` 绑定选定对象；具体场景依次调用上述 `FarmGame` 正式准备接口 | 记录每条结果、种子和检查点；准备成功才开始买入 |
| 买入原料 | 场景在选定的FarmGame实例上调用 `game.Buy(new CommodityId(CropKind.Wheat, CommodityKind.Raw), 1)`；交易模块真实结算 | `TradeResult.Success`、数量为1；原料总量与可用量各增加1，冻结保持0；钱包总额减少真实 `TotalCents + FeeCents`，即时交易费用为0；此刻加工仍闲置，不假设已立即领取 |
| 加工领取 | 场景请求一个经营秒；统一驱动执行完整 tick，随后刷新 | `GetPlot(anchor).RemainingSeconds` 大于0，`GetProcessorDetails(anchor)` 为加工中；原料减少1，产品仍0，该 tick 的 `Produced` 为0；这是完整领取路径的结果 |
| 推进加工并观察成品 | 场景按检查点请求 tick，统一驱动执行；到首个完成批次的 tick 后停止推进 | `TickResult.Produced` 为1、目标产品总量和可用量为1、冻结0；原料仍0且该场不再处于加工中。等待上限作为待确认输入，超限报告当前状态，不强制完成 |
| 创建一次卖单 | 场景通过 `CreateTradeOrder()` 建单：小麦产品、一次、固定数量1、无买入预算、固定现金保留0；条件为商品总库存≥1 | 成功返回本单ID；按ID读取快照为 Waiting；本单冻结数量1；产品总量仍1、可用0、冻结1；资金不因创建卖单变化，`LastFill` 为空 |
| 等待真实卖出 | 场景请求下一完整 tick；订单模块在 tick 尾部正常执行 | 本单 Completed、`LastFill` 商品/方向/成功/数量与本例一致、本单冻结归零；产品总量/可用/冻结均0 |
| 核对结算并报告 | 场景读取同一检查点的余额、库存、订单、加工、日历与行情快照 | 钱包总额比成交前增加 `LastFill.Trade.TotalCents - LastFill.Trade.FeeCents`；这里的TotalCents是货值，费用另列。无其他订单/资金操作时，当前余额等于 `LastFill.BalanceCents`。使用真实货值与费用核对净收入，不再计算1%或报价算法；同时核对总量＝可用＋冻结等关系 |

每次 tick 均经过所有正常经营相位；准备条件消除了其他生产和订单的干扰，而不是删掉这些相位。加工场与农田快照不能混用，按锚点解析唯一实例，不按九个子格重复计数。等待阶段逐 tick 观察，不能等多步后只看最终库存而漏掉实际首个批次。

本例的精确余额/库存断言依赖上述受控条件。在一般现场，其他设施入库、订单成交与同 tick 后续订单都会改变余额或库存，不能把 `LastFill.BalanceCents` 无条件等同于最终钱包，也不能把全部变化归因于本场景。真实拒绝、条件未满足或等待超限要分别报告；正常业务拒绝本身不证明代码缺陷。

| 已有真实完整 tick 与时间/行情快照 | `AdvanceTick()`、`Calendar`、`GetMarketSnapshot()`、`GetWorkers()`、年度表与农田排程查询 | 能解释 tick 结束后的结果；`TickResult` 是本秒汇总，不是逐实例或逐订单事件，复杂现场不能只凭汇总确定归属 |
| 可传入种子，但未公开实际种子 | `FarmGame(int? marketSeed)`；内部构造可传初始秒，但正式主场景无此启动入口 | 独立局可记录显式输入；当前随机种子无法直接查询。若选现场可复现报告，实际种子查询是候选缺口，指定初始秒不等于回放过去 |
| 现有快照分散读取 | 各模块独立只读快照；暂无一次性全局诊断快照 | 简单流程可在稳定检查点顺序读取并记录同一经营秒；需要更复杂现场一致视图时再讨论最小聚合快照，不先开放整个内部对象图 |
| 当前无流程宿主与暂停单步 | `Main.OnTick()` / `RefreshAfterGameChange()` 为私有；`AdvanceTick()` 暂停即返回；[工人表现](../../../scripts/world/WorkerPresentation.cs) 暂停先返回 | 如选择当前局流程，需要接入统一驱动和刷新；如选择暂停单步，还需完整暂停协调与表现同步，不能宣称这些能力已经存在 |
| 没有现场完整复制/恢复 | 当前没有存档与状态导出/导入；内部满地图夹具并非完整现场克隆 | 现场转独立局的完整复制不是现成功能；不把无此能力视为必须先建设完整存档系统 |

## 衔接现有测试

现有[测试汇总](../../../tests/TestSuite.cs)按 `RunChecks()` / `RunChecksAsync()` 调用单元、集成和 e2e，最终以退出码反馈；[现有测试脚本](../../../tools/Run-Tests.ps1)运行指定 Godot headless 场景并生成覆盖率。本设计不替换这些入口，不把整个 TestSuite 搬进玩家正在运行的主场景。

- 单元层继续验证规则本身，例如 [TestTradingService](../../../tests/unit/TestTradingService.cs) 的真实结算与容量、[TestTradeOrders](../../../tests/unit/TestTradeOrders.cs) 的冻结与成交；其 `CheckGameplayPhases()` 已覆盖暂停不自动执行、订单买入晚于加工领取、冻结原料不能加工等关键时点。场景不重复写这些算法的断言大全。
- 经营路径的现有检查，如 [TestFarmGame](../../../tests/unit/TestFarmGame.cs) 的加工保留线/建造领取与公共推进，仍是本例依赖的规则依据；跨模块流程只检查本流程的可观察结果及状态关系。
- 集成层继续检查驱动、地图与 [TestWorkerPresentation](../../../tests/integration/TestWorkerPresentation.cs) 等表现联动；e2e 的 [TestCoreLoop](../../../tests/e2e/TestCoreLoop.cs) 已通过真实 Main、按钮和 Timer 信号检查经营界面，后续仅在选定工具入口后增加对应启动/进度/中止/刷新验收。
- 如果此具体流程以后成为稳定回归需求，可以由现有测试入口调用同一流程逻辑并读取报告，测试侧只负责夹具、受控推进和映射成功/失败；不再实现一份不同的买入加工卖出脚本。共享规则断言若确有重复，再提取最小检查函数，不先迁移全部测试。

测试在无 Main 计时器的独立夹具中顺序调用公共 tick，和工具在当前局通过统一驱动推进，是同一执行路径的不同调用环境。测试可控驱动的存在不允许现场工具并行推进。现有覆盖率/性能/构建验收继续保持；dev 流程可被 Debug 测试调用，不要求把 dev 产物加入 CI。

## 自动调试报告及分析边界

建议形成一个具体流程的报告数据，不预先定义通用报告平台。报告目录已暂定，已确认先只输出JSON，详见[参数化设计](developer-tools-parameterized-tests.md#配置源码文档与报告分开)；报告与 #82 的业务 `.log` 日志职责不同，关联日志只能引用真实会话/事件，不能生成不存在的记录。

| 建议字段 | 内容与含义 |
| --- | --- |
| 流程与版本 | 场景名称、本例版本、代码提交/构建类型；未知值明确缺失 |
| 运行对象与初始化 | 当前局/独立局、显式请求及已知实际种子、准备操作、初始化或开始检查点；引用持久配置的标识/修订/路径和加载时摘要，不复制配置；现场种子未知不填0 |
| 操作序列 | 步骤号、真实入口、参数、返回结果、执行前后经营秒；包括准备、暂停控制和每次实际 tick |
| 执行状态 | 完成、准备不满足、操作拒绝、检查不一致、等待超限、中止或异常；不得将未执行步骤标为通过 |
| 失败位置 | 第一个失败步骤/检查点、相关累计经营秒、已推进 tick 数；LastFill 未带 tick 时记录首次观察到成交的完整 tick |
| 预期与实际 | 例如“产品冻结数量应为1，实际为0”，标注该检查所依赖的前置条件与真实结算结果 |
| 关键模块快照 | 商品总/可用/冻结与底线，钱包三项金额，加工锚点/状态/剩余秒，相关订单和LastFill，日历、行情；必要时补工人/排程快照 |
| 单位与标识 | 金额整数分、数量份、累计经营秒、基础格与实例锚点、本局订单ID，明确区分；快照按检查点保存，不在导出时重读当前值 |
| 状态影响与未验证项 | 现场已发生的变更、停止后的对象状态、未执行步骤、缺失种子/快照及相关限制；不承诺回滚或完整回放 |
| 诊断结论 | 检查证据、可能影响的模块和待调查项；没有进一步证据时根因保持未确定 |

自动执行是按步骤完成操作，自动检查是将观察结果与本例约定比较；两者都不等于根因定位。例如“本单冻结未释放”只说明观察到的关系不一致，还需结合结算、其他订单和快照时点定位。不能仅凭流程失败就断言库存模块、订单模块或某个方法出错，也不能把一个流程通过等同于整个经营系统正确。

## 确认状态与后续设计边界

当前整体设计没有新的待决策问题。首个流程已选择，参数化、现场正常输入与证据不足标准已确认；报告路径暂定、配置只引用不复制，现场手动改速中断整个自动流程，报告先只输出JSON。

两种对象的具体接入、参数字段和窗口呈现仍是设计建议，不将其当作已授权实施。时间接口、实现及开发倍率上限归#100；最小诊断扩充只在真实检查缺口需要时评估。完成/中止不自动改变玩家现场暂停状态，不回滚资源。

本轮仅核对源码并完成文档静态检查与独立审查，不执行上述流程、不运行新工具，也不声称验证过其运行行为。后续代码和构建修改必须另获授权并在实施 issue 中明确。
